Was ist Systemdesign? Vom Laptop zur Cloud

Auf dem Entwickler-Laptop läuft eine Anwendung meist einfach:

  • 1 lokaler Python-Prozess (python app.py)
  • 1 lokale SQLite-Datei
  • 1 gleichzeitiger Nutzer (der Entwickler selbst!)

Die Realität am Valentinstag bei Ada:

  • 50.000 Kunden suchen gleichzeitig nach Blumensträußen.
  • 500 Bestellungen pro Sekunde treffen im Checkout ein.
  • Wenn der Server abstürzt, verliert Ada tausende Euro Umsatz pro Minute!

Systemdesign fügt einzelne Softwarekomponenten und Services zu einer hochverfügbaren, skalierbaren Gesamtlösung zusammen.

Die 3 Kernmetriken des Systemdesigns:

  1. Skalierbarkeit (Scalability):
    Kann das System mit 10-mal oder 100-mal mehr Anfragen umgehen, ohne zusammenzubrechen?
  2. Hochverfügbarkeit (High Availability):
    Läuft das System auch dann weiter, wenn einzelne Server oder ein ganzes Rechenzentrum ausfallen?
    (99.9% Verfügbarkeit = max. 8,7 Stunden Ausfallzeit pro Jahr).
  3. Latenz (Latency):
    Wie viele Millisekunden vergehen zwischen dem Klick des Nutzers und der Antwort im Browser?
    (Industriestandard: Antwortzeit unter 200 ms).

System First, Components Second: Die Entwurfshierarchie

Warum entwirft man das System VOR den Komponenten?

  • Die typische Anfängerfalle:
    • Man beginnt sofort mit Klassen: class Order, class Flower, class Customer.
    • Man weiß aber noch gar nicht: Läuft alles in einem Prozess? Wo werden Daten gespeichert? Welche Latenzen sind gefordert?
    • Folge: Man baut starre Klassenstrukturen, die zerbrechen, sobald Netzwerk, Caching oder verteilte Datenbanken ins Spiel kommen.
  • Die System-First-Methode:
    • Zuerst definieren wir die Leitplanken des Gesamtsystems: Servicegrenzen, synchrone vs. asynchrone Datenflüsse, Persistenz und Skalierungsanforderungen.
    • Erst wenn das Makro-Design steht, entwerfen wir die internen Klassen und Komponenten (Mikro-Design).

Skalierung im Vergleich: Scale Up vs. Scale Out

1. Vertikale Skalierung (Scale Up)

"Kauf einen größeren Server!"

  • Man rüstet dieselbe Maschine auf: 128 CPU-Kerne, 1 TB RAM, schnellere SSDs.
  • Vorteile:
    • Keine Software-Architekturänderung nötig.
    • Keine Netzwerkverzögerung zwischen Services.
  • Nachteile & Grenzen:
    • Physikalische Obergrenze: Mehr als die größte verfügbare Maschine geht nicht!
    • Astronomische Kosten: Verdopplung der Leistung kostet oft das Vierfache.
    • Single Point of Failure (SPoF): Fällt dieser eine Server aus, steht das gesamte Unternehmen still!

2. Horizontale Skalierung (Scale Out)

"Nimm viele normale Server!"

  • Eine Flotte kleiner Instanzen hinter einem Load Balancer, der die Anfragen verteilt.
  • Vorteile:
    • Nahezu unbegrenzt erweiterbar: Bei Lastspitzen starten automatisch neue Instanzen (Auto-Scaling).
    • Ausfallsicherheit: Fällt eine Instanz aus, übernehmen die restlichen Server ohne Ausfallzeit.
  • Herausforderung:
    • Die Anwendungslogik muss zustandslos (stateless) sein! Sitzungsdaten dürfen nicht im Arbeitsspeicher des Webservers liegen, sondern gehören in einen zentralen Cache (Redis).

Die Architektur-Trade-offs:

  • Der Monolith:
    • Gut für kleine Teams: Einfaches Deployment (1 Befehl), einfaches Debugging.
    • Schlecht bei Wachstum: Ein Speicherleck im AI-Modul reißt den gesamten Checkout mit in den Abgrund!
  • Microservices:
    • Unabhängige Teams & Skalierung: Der hochfrequentierte Katalog skaliert auf 20 Instanzen, während der Checkout auf 3 Instanzen läuft.
    • Fehlertoleranz: Fällt der Lager-Service aus, können Kunden im Webshop trotzdem stöbern.

Die 5 Stufen im architektonischen Detail

Stufe 1: Single Instance Monolith

  • Setup: Eine EC2-Instanz oder Hetzner-Server. Python, SQLite/PostgreSQL und Bilddateien liegen auf derselben Festplatte.
  • Grenze: Fällt der Server aus $\to$ Totalausfall (SPOF). CPU/RAM-Limit erreicht $\to$ System stürzt ab.

Stufe 2: State Extraction (Zustandslosigkeit)

  • Setup: Die Datenbank wandert zu Amazon RDS, Bilder zu Amazon S3.
  • Gewinn: Der Webserver speichert keine persistenten Daten mehr. Er kann jederzeit neu gestartet oder ersetzt werden!

Stufe 3: Horizontale Skalierung

  • Setup: Ein Application Load Balancer (ALB) verteilt Traffic auf 2 bis 20 Webserver. Nutzersitzungen liegen in einem Redis In-Memory-Cluster.
  • Gewinn: Hohe Ausfallsicherheit und Bewältigung von Lastspitzen.

Stufe 4: Container & Microservices

  • Setup: Aufteilung in Bounded Contexts (Katalog, Checkout, Lager) als Docker-Container auf AWS ECS oder Kubernetes.
  • Gewinn: Teams deployen unabhängig; Komponenten mit Speicherlecks reißen andere nicht mit.

Stufe 5: Serverless & Event-Driven

  • Setup: AWS Fargate für containerisierte REST-APIs, AWS Lambda für asynchrone Hintergrundjobs (z. B. Bildanalyse bei Upload), EventBridge & SQS zur Pufferung.
  • Gewinn: Zero-Server-Management, automatische Skalierung von 0 auf 10.000 Instanzen in Sekunden, Pay-per-Use (0 € Kosten bei Inaktivität!).

Trade-off-Matrix: Wann lohnt sich welcher Schritt?

Stufe Entwicklungsaufwand Betriebskosten (Basis) Skalierbarkeit Ausfallsicherheit Wann einsetzen?
1. Single Instance Sehr gering (1 Tag) Sehr niedrig (~5–10 €/Monat) Minimal (nur vertikal) Gering (SPOF) MVP, Prototypen, Uni-Projekte
2. State Extraction Gering (1–2 Tage) Niedrig (~30–50 €/Monat) Mittel Gut (DB gesichert) Erste echte Nutzer, Startup-Start
3. Horiz. Skalierung Mittel (1–2 Wochen) Moderat (~100–300 €/Monat) Sehr hoch (Web-Tier) Sehr hoch (Multi-AZ) Wachsende Shops, Lastspitzen
4. Container/K8s Hoch (mehrere Wochen) Hoch (~300–1.000 €/Monat) Exzellent Exzellent Große Entwicklerteams, viele Services
5. Serverless Mittel bis hoch Pay-per-Use (0 € bis variabel) Nahezu unbegrenzt Höchste (Cloud-nativ) Unvorhersehbare Last, Event-Driven

Praxis-Faustregel: Beginnen Sie so einfach wie möglich (Stufe 1 oder 2), aber entwerfen Sie den Code von Tag 1 an modular und zustandslos (Modul 3). Dann können Sie jederzeit ohne Neuschreiben des Fachcodes auf Stufe 3, 4 oder 5 wechseln!

Cloud-Native Paradigmen: Pets vs. Cattle

🐶 Das klassische Paradigma: Pets (Haustiere)

  • Früher gaben Administratoren ihren Servern Kosenamen ("Server-Zeus", "Athena").
  • Jeder Server wurde manuell per SSH konfiguriert und gepflegt.
  • Wenn "Zeus" krank wurde oder abstürzte:
    • Panik im gesamten Team!
    • Nachtschichten zur manuellen Wiederbelebung.
    • Hohes Risiko von unerwünschten Konfigurationsabweichungen (Configuration Drift).

🐮 Das Cloud-Native Paradigma: Cattle (Nutztiere)

  • Server und Container haben keine Namen, sondern zufällige IDs (i-0a8b9c1d2e).
  • Sie werden vollautomatisch aus standardisierten Bauplänen (Docker Images / AMI) gestartet.
  • Wenn eine Instanz nicht mehr reagiert:
    • Nicht reparieren, sondern terminieren!
    • Der Load Balancer wirft die Instanz raus.
    • Das Auto-Scaling startet sofort einen frischen Ersatz.
  • Regel: Kein Server ist unersetzbar!

Cloud-Native Prinzip: Zustandslosigkeit (Statelessness)

Damit ein System horizontal skalieren und Instanzen beliebig beenden kann, müssen Anwendungsserver zustandslos (stateless) sein:

❌ Verboten auf Cloud-Native Servern:

  • Lokale Session-Speicherung: Der Login-Status eines Nutzers liegt im Arbeitsspeicher von Server 1. Schickt der Load Balancer den nächsten Klick an Server 2, fliegt der Kunde raus!
  • Lokales Dateisystem (/tmp/uploads): Wenn ein Kunde ein Bild hochlädt und der Server stirbt, ist das Bild für immer verloren.
  • Hintergrund-Threads im Prozess: Brechen ab, wenn die Instanz herunterskaliert wird.

✅ Die Lösung: Externe Zustandsspeicherung

Browser (Kunde)
      │
      ▼
Load Balancer (ALB)
      │
      ├───────────────────────┐
      ▼                       ▼
Instanz 1 (Stateless)   Instanz 2 (Stateless)
      │                       │
      ├───────────┬───────────┤
      ▼           ▼           ▼
   [Redis]      [S3]     [PostgreSQL]
  (Sessions)  (Bilder)   (Bestelldaten)
  • Vorteil: Jeder Server kann jederzeit abstürzen oder neu starten – kein Nutzer merkt einen Unterschied!

Das C4-Modell für Architekturdokumentation

Klassische UML-Diagramme sind für moderne Cloud-Architekturen oft zu detailreich oder unübersichtlich.
Das C4-Modell (Simon Brown) nutzt das Prinzip von Google Maps:

  • Stufe 1: System Context (Weltkarte)
    Wer nutzt das System? Welche Fremdsysteme sind angebunden?
  • Stufe 2: Container (Stadtplan)
    Welche eigenständigen Einheiten (Web-App, API-Server, Datenbanken, Caches, Queues) existieren?
  • Stufe 3: Component (Straßenansicht)
    Aus welchen Controllern, Services und Repositories besteht ein einzelner Container?
  • Stufe 4: Code (Gebäudeplan)
    UML-Klassendiagramme für komplexe interne Klassen.

Sequenzdiagramme im Systemdesign (Einführung)

Während Architekturdiagramme zeigen, welche Komponenten existieren, zeigen Sequenzdiagramme, wie diese Komponenten zeitlich interagieren:

Die Kern-Elemente eines Sequenzdiagramms:

  1. Lebenslinie (Lifeline):
    Vertikale gestrichelte Linie unter jedem Teilnehmer (participant oder actor). Zeit verläuft von oben nach unten.
  2. Synchrone Nachricht (->>):
    Aufrufer wartet blockierend auf die Antwort (z. B. HTTP-Request).
  3. Antwort-Nachricht (-->>):
    Rückgabe der Daten (z. B. HTTP 200 OK mit JSON-Payload).
  4. Asynchrone Nachricht:
    Nachricht wird gesendet (z. B. Event in Message Queue), ohne auf Fertigstellung zu warten.

Sequenzdiagramme: Fragmente (alt, loop, opt)

Aus den ursprünglichen Vorlesungsfolien (Systemdesign.txt): Wie modelliert man Schleifen und Verzweigungen im Sequenzdiagramm?

Die wichtigsten Kontroll-Fragmente:

  • alt ... else ... end (Alternative):
    Bedingte Verzweigung (If-Else). Genau ein Zweig wird ausgeführt (z. B. Zahlung erfolgreich vs. abgelehnt).
  • opt ... end (Optional):
    Wird nur ausgeführt, wenn eine Bedingung zutrifft (If ohne Else, z. B. Prio-Zustellung für Express-Kunden).
  • loop ... end (Schleife):
    Wiederholt die Interaktion bis zum Abbruch (z. B. Polling oder Retry bei Netzwerkfehlern).

Syntax-Beispiel in Mermaid:

sequenceDiagram participant App participant Bank App ->> Bank: Prüfe Deckung(Betrag) alt Betrag <= Kontostand Bank -->> App: Buchung bestätigt (200 OK) else Überzogen Bank -->> App: Abgelehnt (402 Payment Required) end opt Kunde will SMS-Beleg App ->> Bank: Sende Bestätigungs-SMS end

Analyse des Workflows:

  • Atomare Bestandsreservierung: Der Bestand wird vor der Zahlung reserviert, damit kein anderer Kunde die letzte Pflanze wegschnappt.

Datenbankentwurf im Systemdesign

Aus Systemdesign.txt: Im Systemdesign plant man Datenbanken nicht nach Klassen, sondern nach Abfragemustern (Queries)!

Die Grundregel:

"Überlege dir zuerst, welche Fragen das System schnell beantworten muss, bevor du Tabellen anlegst!"

Relational (SQL) vs. NoSQL (Key-Value / Document):

  • Relational (PostgreSQL, MySQL):
    • Perfekt für Finanztransaktionen, Aufträge und Beziehungen (Foreign Keys).
    • ACID-Garantien schützen vor Race Conditions und inkonsistenten Daten.
  • Key-Value Store (Redis):
    • Extrem schnell für einfache Abfragen per Schlüssel (GET plant:101).

Tabellen-Design für Ada's Onlineshop:

-- 1. Tabelle für Pflanzen (Katalog)
CREATE TABLE plants (
    id VARCHAR(32) PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price_cents INT NOT NULL,
    stock_qty INT NOT NULL CHECK (stock_qty >= 0)
);

-- 2. Tabelle für Bestellungen
CREATE TABLE orders (
    id VARCHAR(32) PRIMARY KEY,
    customer_email VARCHAR(120) NOT NULL,
    total_cents INT NOT NULL,
    status VARCHAR(20) DEFAULT 'PENDING',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
  • PRIMARY KEY garantiert schnelle Indizierung und Eindeutigkeit.

Caching-Konzepte: Warum In-Memory?

Das Lastprofil eines Onlineshops:

  • Read-to-Write Ratio: 100 : 1.
  • 10.000 Besucher stöbern durch den Pflanzenkatalog (Read).
  • Nur 100 Kunden schließen am Ende eine Bestellung ab (Write).

Das Problem:

Wenn jeder Katalog-Aufruf eine komplexe SQL-Abfrage mit JOIN an PostgreSQL schickt, bricht die Datenbank unter Last zusammen!

Die Latenz-Hierarchie (In-Memory vs. Disk):

  • RAM (Redis): Zugriff in wenigen Mikrosekunden (< 1 ms).
  • NVMe SSD: Zugriff in 10 bis 50 Millisekunden (10.000 µs).
  • ⇒ RAM ist um den Faktor 1.000 schneller!

Die Cache-Regel für Architekten:

          [ Browser / Client ]
                   │
                   ▼
       [ Storefront API (FastAPI) ]
                   │
       ┌───────────┴───────────┐
       ▼                       ▼
95% aller Anfragen      5% aller Anfragen
  (Read-Hit)              (Cache-Miss / Write)
       │                       │
       ▼                       ▼
 [ Redis Cache ]        [ PostgreSQL DB ]
   (Latenz < 1 ms)        (Latenz ~ 30 ms)
  • Durch Caching werden 95 % des Traffics von der teuren relationalen Datenbank ferngehalten!

Caching mit Redis: Das Cache-Aside-Muster

Das Cache-Aside-Muster (Lazy Loading) ist der Standard für zustandslose Web-Backends:

  1. Anfrage kommt an: Die Anwendung prüft zuerst, ob der Datensatz im Redis-Cache liegt.
  2. Cache Hit (Treffer): Datensatz liegt im Cache ⇒ Direkt aus dem RAM als JSON an den Client zurückgeben.
  3. Cache Miss (Fehlschlag): Datensatz fehlt im Cache:
    • Daten aus der relationalen PostgreSQL-Datenbank laden.
    • Für künftige Anfragen im Redis-Cache ablegen (mit Ablaufzeit / TTL).
    • Daten an den Client zurückgeben.
import json
import redis

# Verbindung zum In-Memory-Cache:
r = redis.Redis(host='localhost', port=6379, db=0)

def hole_pflanzen_details(pflanze_id: str) -> dict:
    cache_key = f"plant:{pflanze_id}"
    
    # 1. Zuerst im Cache nachsehen (Cache Hit?):
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)
        
    # 2. Cache Miss: Aus langsamer SQL-Datenbank laden:
    print("⚠️ Cache Miss: Lade aus PostgreSQL...")
    daten = db.query_plant_by_id(pflanze_id)
    
    # 3. Für 10 Minuten (600 Sekunden) im Cache ablegen:
    r.setex(cache_key, 600, json.dumps(daten))
    return daten

Cache-Invalidierung & Konsistenz

"There are only two hard things in Computer Science: cache invalidation and naming things."
(Phil Karlton)

Das Problem veralteter Daten (Stale Data):

Ada reduziert den Preis der Monstera im Admin-Panel von 40 € auf 25 €.
Im Webshop sehen Kunden aber noch 10 Minuten lang 40 €, weil der alte Preis im Redis-Cache festhängt!

Die 2 Lösungsstrategien:

  1. TTL (Time-To-Live / Verfallszeit):
    Jeder Cache-Eintrag verfällt automatisch nach z. B. 300 Sekunden. Gut als Sicherheitsnetz.
  2. Aktive Invalidierung bei Updates:
    Wird ein Datensatz in PostgreSQL geändert, löscht der Schreibservice sofort den passenden Schlüssel in Redis!

Praxisbeispiel: Preis-Update mit Invalidierung

def aktualisiere_pflanzen_preis(pflanze_id: str, 
                                neuer_preis: float):
    # 1. Haupt-Datenbank aktualisieren (Single Source of Truth):
    db.execute(
        "UPDATE plants SET price = %s WHERE id = %s",
        (neuer_preis, pflanze_id)
    )
    
    # 2. Cache aktiv löschen (Cache Invalidation):
    cache_key = f"plant:{pflanze_id}"
    r.delete(cache_key)
    print(f"🧹 Cache-Schlüssel {cache_key} gelöscht!")
    
    # Nächster Seitenaufruf holt garantiert 
    # den neuen Preis aus der Datenbank!

RESTful APIs: Grundlagen & HTTP-Verben

REST (Representational State Transfer) ist der globale Architektur-Standard für Webservices über das HTTP-Protokoll.

Die 4 wichtigsten HTTP-Methoden:

  • GET /api/v1/plants
    Ressourcen abrufen (Safe & Idempotent: Ändert niemals Daten).
  • POST /api/v1/orders
    Neue Ressource erzeugen (Nicht idempotent: Jeder Aufruf legt eine neue Bestellung an!).
  • PUT /api/v1/plants/{id}
    Ressource vollständig überschreiben (Idempotent).
  • DELETE /api/v1/plants/{id}
    Ressource löschen (Idempotent).

Die HTTP-Statuscodes für Entwickler:

  • 2xx (Erfolg):
    • 200 OK: Erfolgreich abgerufen oder geändert.
    • 201 Created: Neue Ressource erfolgreich angelegt.
    • 202 Accepted: Auftrag zur asynchronen Verarbeitung angenommen.
  • 4xx (Client-Fehler):
    • 400 Bad Request: Ungültiges JSON oder Validierungsfehler.
    • 401 Unauthorized: API-Token fehlt oder ist abgelaufen.
    • 404 Not Found: Ressource existiert nicht.
  • 5xx (Server-Fehler):
    • 500 Internal Server Error: Unbehandelter Fehler im Backend.
    • 503 Service Unavailable: Server überlastet oder Wartung.

Schema-Validierung mit Pydantic

In modernem Python (FastAPI) schreiben wir JSON-Schemas nicht als unleserlichen Text, sondern als Pydantic-Klassen:

  • Automatische Typkonvertierung: String "42" wird automatisch zu int 42.
  • Präzise Validierung: Grenzwerte (gt, le), E-Mail-Formate und Regex-Muster direkt deklariert.
  • Automatische 422-Fehler: Ungültige Anfragen werden vom Framework abgewiesen, bevor sie die Fachlogik erreichen!
  • Automatische OpenAPI-Dokumentation (Swagger UI).
from pydantic import BaseModel, Field, HttpUrl

# Verbindliche Request-Struktur:
class DiagnoseRequest(BaseModel):
    plant_id: str = Field(min_length=3, max_length=32)
    image_url: HttpUrl

# Verbindliche Response-Struktur:
class DiagnoseResponse(BaseModel):
    diagnosis: str
    confidence: float = Field(ge=0.0, le=1.0)
    action: str

# Im FastAPI-Backend:
@app.post("/api/v1/diagnose", response_model=DiagnoseResponse)
def diagnose_plant(req: DiagnoseRequest):
    # 'req' ist zu 100% typsicher und validiert!
    result = ai_service.analyze(req.image_url)
    return DiagnoseResponse(
        diagnosis=result.label,
        confidence=result.score,
        action=result.recommendation
    )

AI Inference APIs: Besondere Entwurfsregeln

Was unterscheidet einen Aufruf an ein AI-Modell (LLM / Vision) von einer normalen Datenbankabfrage?

  1. Hohe Latenz:
    Ein Vision-Modell braucht 2 bis 6 Sekunden für die Bildanalyse (statt 20 ms in SQL).
  2. Kosten pro Token / Inferenz:
    Jeder Aufruf kostet echtes Geld (z. B. 0,02 € pro Bildanalyse). Schutz vor Missbrauch zwingend nötig!
  3. Probabilistische Antworten:
    Das Modell antwortet nicht deterministisch; Ausgaben müssen strikt mit Pydantic-Schemas validiert werden.

Architekturlösungen für AI-Endpunkte:

  • Token-Streaming (Server-Sent Events / SSE):
    Textfragmente werden sofort gestreamt, sobald sie berechnet sind. Der Nutzer sieht das Ergebnis live wachsen!
  • Asynchrone Job-Verarbeitung:
    Bei Bild-Uploads gibt das Backend sofort 202 Accepted mit einer Job-ID zurück; das Frontend pollt oder nutzt WebSockets.
  • Graceful Degradation:
    Fällt die externe KI-API aus, darf der Checkout nicht crashen! Fallback: Standard-Floristentipps anzeigen.

Autonome AI-Agenten: Das ReAct-Pattern

Ein AI-Agent nutzt ein Sprachmodell als Reasoning Engine, um selbstständig komplexe Ziele zu erreichen, indem er Werkzeuge (Tools / Function Calling) aufruft.

Das ReAct-Muster (Reasoning + Acting):

  1. Thought (Überlegung):
    Das LLM analysiert das Ziel: "Der Bestand von Ficus Benjamini ist auf 2 Stück gefallen. Ich muss Großhändlerpreise prüfen."
  2. Action (Werkzeugaufruf):
    Ruft ein getyptes Tool auf: query_supplier_prices(item_id="FIC-10").
  3. Observation (Beobachtung):
    Nimmt das Ergebnis entgegen: [{"supplier": "A", "price": 12.50}].
  4. ⇒ Wiederholt die Schleife, bis das Ziel erreicht ist!

AI-Sicherheit: Human-in-the-Loop (HITL)

Das Problem unbeschränkter Autonomie:

  • Ein KI-Agent mit unkontrolliertem Zugriff könnte versehentlich 10.000 Ficus-Pflanzen für 120.000 € bestellen!
  • Prompt Injections oder Halluzinationen können Fehlentscheidungen auslösen.

Das Prinzip: Human-in-the-Loop (HITL)

  • Klare Budgetgrenzen im Backend verankern:
    • Bestellwert ≤ 500 €: Der Agent darf autonom bestellen.
    • Bestellwert > 500 €: Die Transaktion wird pausiert; Ada erhält eine Push-Nachricht zur manuellen Freigabe!
  • Geschäftsregeln gehören in den Backend-Code, niemals nur in den LLM-System-Prompt!
from pydantic import BaseModel, Field

class OrderRequest(BaseModel):
    item_id: str
    quantity: int = Field(gt=0, le=100)
    max_price_per_unit: float

def execute_agent_order(req: OrderRequest) -> str:
    total = req.quantity * req.max_price_per_unit
    
    # Hartes Sicherheitslimit im Python-Code:
    if total > 500.0:
        ticket = create_approval_ticket(total, req)
        return f"⏳ Genehmigung erforderlich! Ticket #{ticket.id} erstellt."
        
    order_id = supplier_api.place_order(req.item_id, req.quantity)
    return f"✅ Autonom bestellt: Order #{order_id} ({total:.2f} €)"
