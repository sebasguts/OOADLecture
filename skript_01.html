Das Problem ohne OO: Datenchaos mit Dictionaries

Anfänger beginnen oft mit simplen Dictionaries.
Warum führt das in echten Projekten schnell zur Katastrophe?

  • Keine Typprüfung: Man kann versehentlich Strings statt Zahlen übergeben.
  • Tippfehler in Schlüsseln: "pries" statt "preis" legt stillschweigend einen neuen Key an – ein stiller Logikfehler.
  • Fehlende Kapselung: Jeder Programmteil kann den Zustand manipulieren (z. B. negativer Preis).
  • Verhalten und Daten sind getrennt: Funktionen liegen lose verstreut herum.
# ❌ Schlechter, unstrukturierter Code:
pflanze_1 = {
    "name": "Monstera Deliciosa",
    "preis": 29.99,
    "feuchtigkeit": 45
}

# Typischer Bug: Schreibfehler im Key!
pflanze_1["pries"] = -50.0  # Kein Fehler zur Laufzeit!

def giesse_pflanze(p: dict, menge: int):
    # Keine Garantie, dass die Keys existieren
    p["feuchtigkeit"] += menge

giesse_pflanze(pflanze_1, 20)
print(pflanze_1["feuchtigkeit"])  # 65

Was ist Objektorientierung?

Objektorientierung (OO) ist die Modellierung eines Softwaresystems durch kooperierende Objekte, die Zustand (Daten) und Verhalten (Methoden) zu einer Einheit bündeln.

  • Zustand (State): Die internen Daten eines Objekts zu einem bestimmten Zeitpunkt (z. B. Wasserstand = 45%, Preis = 29.99 €).
  • Verhalten (Behavior): Was das Objekt tun kann (z. B. bewaessern(), berechne_endpreis()).
  • Identität (Identity): Jedes Objekt ist eindeutig unterscheidbar, selbst wenn alle Attribute identisch sind (im Speicher an unterschiedlichen Adressen).

Die Alltagsanalogie: Zimmerpflanze im Topf

  • Zustand:
    • Art: Monstera
    • Erdfeuchtigkeit: 30 %
    • Standort: Halbschatten
  • Verhalten:
    • Verbraucht Wasser über Zeit
    • Nimmt Wasser beim Gießen auf
    • Zeigt Welkesymptome bei < 20 %
  • Identität:
    • Zwei Töpfe mit identischer Monstera nebeneinander sind trotzdem zwei verschiedene Pflanzen!
    • Im Code: p1 == p2 (Wertegleichheit via __eq__) vs. p1 is p2 (Identität / Speicheradresse id(p)).

Klassen vs. Instanzen

Klasse = Der Bauplan

  • Definiert, welche Attribute und Methoden Objekte dieses Typs besitzen.
  • Existiert im Quellcode als Schablone.
  • Analogie: Die Ausstechform für Plätzchen oder der Bauplan eines Hauses.

Instanz / Objekt = Das konkrete Exemplar

  • Wird zur Laufzeit im Arbeitsspeicher nach dem Bauplan erzeugt.
  • Besitzt konkrete Werte für die Attribute.
  • Analogie: Das fertige Plätzchen oder das gebaute Haus in einer Straße.
# Die KLASSE (Der Bauplan):
class Pflanze:
    def __init__(self, name: str, preis: float):
        self.name = name          # Attribut
        self.preis = preis        # Attribut

    def beschreibe(self) -> str: # Methode
        return f"{self.name} für {self.preis:.2f} €"

# INSTANZEN (Konkrete Objekte im Speicher):
monstera = Pflanze("Monstera Deliciosa", 29.99)
ficus = Pflanze("Ficus Benjamini", 19.95)

print(monstera.beschreibe())
# -> Monstera Deliciosa für 29.99 €
print(ficus.beschreibe())
# -> Ficus Benjamini für 19.95 €

Kapselung (Encapsulation) & Properties

Kapselung verbirgt interne Datenstrukturen vor Außenstehenden und erlaubt Zugriff nur über kontrollierte Schnittstellen.

  • Schutz vor Inkonsistenz: Niemand darf den Preis auf null oder einen negativen Betrag setzen!
  • Verstecken von Komplexität: Der Aufrufer muss nicht wissen, wie der Wert intern gespeichert wird.
  • In Python: Nicht-öffentliche Attribute per Konvention mit führendem Unterstrich (_preis, PEP 8: „internal use“) und Absicherung über @property. Doppelter Unterstrich (__preis) aktiviert Name Mangling – ist aber ebenfalls kein echter Zugriffsschutz.
  • Philosophie: Python erzwingt keine Zugriffsbeschränkung zur Laufzeit ("We are all consenting adults here"). Der Unterstrich signalisiert: Internes Detail, nicht von außen zugreifen!
class Topfpflanze:
    def __init__(self, name: str, preis: float):
        self.name = name
        self.preis = preis  # Ruft Setter auf!

    @property
    def preis(self) -> float:
        """Öffentlicher Getter"""
        return self._preis

    @preis.setter
    def preis(self, wert: float) -> None:
        """Kontrollierter Setter mit Validierung"""
        if wert <= 0:
            raise ValueError("Preis muss positiv sein!")
        self._preis = wert

p = Topfpflanze("Orchidee", 25.0)
# p.preis = -10.0  # 💥 Löst ValueError aus!

Typisierung in modernem Python: Type Hints & PEP 484

Klassisches Python ist dynamisch typisiert: Typen werden erst zur Laufzeit interpretiert.
Seit PEP 484 (Python 3.5) bzw. PEP 526 (Variablen-Annotationen, Python 3.6) verfügt Python über offizielle Type Hints – das Fundament für professionelles Software-Design!

Warum Typisierung in OO unverzichtbar ist:

  • Selbstdokumentation: Parameter und Rückgabetypen sind auf einen Blick glasklar – Typen müssen nicht mehr im Docstring stehen.
  • IntelliSense & Tooling: IDEs bieten präzise Autovervollständigung und sicheres automatisiertes Refactoring.
  • Statische Typprüfung: Tools wie mypy oder pyright finden Typfehler, falsche Attribute und None-Zugriffe vor der Programmausführung!
  • Fundament moderner Frameworks: @dataclass, pydantic und FastAPI basieren auf Type Hints.
# 1. Variablen und Collections (Python 3.9+ Syntax):
alter: int = 42
preis: float = 19.99
pflanzen: list[str] = ["Monstera", "Ficus"]
katalog: dict[str, float] = {"Monstera": 19.99}

# 2. Methoden-Signaturen mit Rückgabetyp:

Modernes Python: Dataclasses & Slots

Früher erforderte jede Python-Klasse mühsamen Boilerplate-Code für __init__, __repr__ und __eq__.

  • @dataclass (seit Python 3.7):
    Generiert Konstruktor, lesbare Ausgabe und Wertevergleich automatisch anhand von Type Hints.
  • slots=True (Python 3.10+):
    Verhindert dynamisches Hinzufügen beliebiger Attribute und spart Speicher (kein __dict__ pro Objekt) – die Ersparnis hängt von Python-Version und Attributzahl ab.
  • kw_only=True (Python 3.10+):
    Erzwingt benannte Parameter beim Aufruf – verhindert Verwechslungen bei vielen Argumenten!
  • Best Practice: Dataclasses ideal für Datenhalter / Value Objects einsetzen; tiefe Vererbungshierarchien mit slots=True vermeiden (Problem mit super() vor Python 3.13).
from dataclasses import dataclass

@dataclass(slots=True, kw_only=True)
class SmartPlant:
    botanischer_name: str
    preis: float
    feuchtigkeits_soll: int = 50
    ist_feuchtigkeit: int = 50

    def muss_gegossen_werden(self) -> bool:
        return self.ist_feuchtigkeit < self.feuchtigkeits_soll

# Instanziierung erfordert Schlüsselwörter:
p = SmartPlant(
    botanischer_name="Monstera", 
    preis=29.99, 
    ist_feuchtigkeit=35
)

print(p)
# -> SmartPlant(botanischer_name='Monstera', ...)
print(p.muss_gegossen_werden())  # True

UML-Klassendiagramme: Die Grundlagen

Die Unified Modeling Language (UML) ist die Weltsprache für Softwareentwurf.

Aufbau einer Klasse in UML:

Ein Kasten mit drei Abschnitten:

  1. Klassenname: Zentriert, fett (kursiv = abstrakt).
  2. Attribute: [Sichtbarkeit] name : Typ
  3. Methoden: [Sichtbarkeit] name(Parameter) : Rückgabetyp

Sichtbarkeitsmodifikatoren (Visibilities):

  • + Public: Überall sichtbar und aufrufbar.
  • - Private: Nur innerhalb dieser Klasse sichtbar.
  • # Protected: In der Klasse und ihren Subklassen sichtbar.
  • ~ Package: Nur innerhalb des Moduls/Pakets sichtbar.

Objektbeziehungen: Wie Klassen miteinander interagieren

In einer professionellen Softwarearchitektur steht keine Klasse isoliert für sich allein. Reale Geschäftslogik entsteht erst durch das Zusammenspiel kooperierender Objekte.

Die 3 Leitfragen zur Modellierung:

  1. Wer kennt wen? (Sichtbarkeit & Kopplung):
    Hält Objekt A eine Referenz auf Objekt B? Weiß B von A (bidirektional) oder nur A von B (unidirektional)?
  2. Wer besitzt wen? (Lebenszyklus & Existenz):
    Kann das Teil ohne das übergeordnete Ganze weiter existieren, oder stirbt es mit ihm?
  3. Wer ist was? (Generalisierung & Verträge):
    Ist Klasse B eine spezielle Variante von A (is-a) oder erfüllt B einen definierten Vertrag (can-do)?

Die Beziehungsarten nach Kopplungsstärke:

  1. Abhängigkeit (sehr lose):
    "Benutzt kurzzeitig" – Nur als Parameter, lokale Variable oder beim Erzeugen (Factory erzeugt Pflanze).
  2. Assoziation (lose):
    "Nutzt / Kennt" – Unabhängige Lebenszyklen (Kunde kennt Pflanze).
  3. Aggregation (mittel):
    "Besteht aus" – Schwache Teil-Ganzes-Beziehung. Teile überleben (Blumenstrauß hat Blumen).
  4. Komposition (stark):
    "Besitzt existenziell" – Strikte Teil-Ganzes-Beziehung. Teile sterben mit (Rechnung besitzt Positionen).
  5. Vererbung (sehr stark):
    "Ist ein" – Feste Code- und Verhaltenskopplung (Zimmerpflanze ist Pflanze).
  6. Realisierung (flexibel):
    "Implementiert / Erfüllt Vertrag" – Polymorphe Schnittstelle (Sensor implementiert Messbar).

Beziehung 1: Assoziation (Kunde kennt Pflanze)

Eine Assoziation ist eine lose Beziehung zwischen zwei unabhängigen Klassen. Beide Objekte besitzen ihren eigenen, unabhängigen Lebenszyklus.

  • Ein Kunde schaut sich Pflanzen an oder legt sie in den Merkzettel.
  • Stirbt der Kunde oder löscht sein Konto, existiert die Pflanze im Laden weiter.
  • Wird die Pflanze verkauft, existiert der Kunde weiter.
  • UML: Einfache Linie oder gerichteter Pfeil (-->).
class Kunde:
    def __init__(self, name: str) -> None:
        self.name = name
        self.merkzettel: list[Pflanze] = []

    def merke(self, p: Pflanze) -> None:
        # Assoziation: Kunde referenziert Pflanze
        self.merkzettel.append(p)

Beziehung 2: Aggregation (Blumenstrauß & Blumen)

Eine Aggregation ist eine "Teil-Ganzes-Beziehung" (has-a), bei der die Teile auch ohne das Ganze existieren können.

  • Ein Blumenstrauss besteht aus mehreren Blume-Objekten.
  • Löst man den Strauß auf, existieren die einzelnen Blumen weiter und können in einen neuen Strauß gebunden werden.
  • Die Blumen werden von außen übergeben (sie existieren unabhängig vom Strauß).
  • UML-Symbol: Eine ungefüllte (weiße) Raute am Ganzen (o--).
  • Hinweis: Die UML 2 lässt die Semantik der Aggregation bewusst offen – in der Praxis wird sie unterschiedlich streng ausgelegt.
class Blumenstrauss:
    def __init__(self, blumen: list[Blume]) -> None:
        # Die Blumen existieren bereits und werden übergeben:
        self.blumen = blumen

    def berechne_preis(self) -> float:
        return sum(b.einzelpreis for b in self.blumen)

Beziehung 3: Komposition (Rechnung & Positionen)

Eine Komposition ist eine strenge existenzielle Teil-Ganzes-Beziehung. Die Teile können nicht ohne das übergeordnete Ganze existieren.

  • Eine Rechnung besitzt mehrere RechnungsPosition-Einträge.
  • Wird die Rechnung im System storniert oder gelöscht, verlieren die Positionen jegliche Existenzberechtigung und werden mitgelöscht.
  • Die Teile werden üblicherweise im Ganzen erzeugt.
  • UML-Symbol: Eine ausgefüllte (schwarze) Raute am Ganzen (*--).
class Rechnung:
    def __init__(self, nr: str) -> None:
        self.nr = nr
        self._positionen: list[RechnungsPosition] = []

    def fuege_position_hinzu(self, text: str, betrag: float) -> None:
        # Das Ganze erzeugt und besitzt seine Teile existenziell:
        pos = RechnungsPosition(text, betrag)
        self._positionen.append(pos)

Beziehung 4: Vererbung / Generalisierung (Pflanze & Zimmerpflanze)

Eine Vererbung (Generalisierung / Spezialisierung) modelliert eine "Ist-Ein"-Beziehung (is-a). Eine Subklasse erbt Attribute und Verhalten der Basisklasse.

  • Eine Zimmerpflanze ist eine Pflanze mit zusätzlichen Attributen (z. B. topf_cm).
  • Änderungen an der Basisklasse wirken sich direkt auf alle Subklassen aus (starke strukturelle Kopplung).
  • UML-Symbol: Ein geschlossener, weißer Dreieckspfeil (<\|--), der zur Basisklasse zeigt.
class Pflanze:
    def __init__(self, name: str, preis: float) -> None:
        self.name = name
        self.preis = preis

class Zimmerpflanze(Pflanze):  # Erbt von Pflanze
    def __init__(self, name: str, preis: float, topf_cm: int) -> None:
        super().__init__(name, preis)
        self.topf_cm = topf_cm

Beziehung 5: Realisierung / Interface-Implementierung

Eine Realisierung (Interface-Implementierung) bedeutet, dass eine Klasse einen formalen Vertrag erfüllt (can-do), ohne Implementierungsdetails von einer Basisklasse zu erben.

  • Ein Interface definiert, was getan werden kann, nicht wie.
  • Mehrere völlig unterschiedliche Klassen können dasselbe Interface erfüllen (Polymorphie).
  • In modernem Python realisiert über typing.Protocol (Duck Typing) oder abc.ABC.
  • UML-Symbol: Eine gestrichelte Linie mit weißem Dreieckspfeil (<\|..), der zum Interface zeigt.
from typing import Protocol

class Messbar(Protocol):
    def lese_wert(self) -> float: ...

class FeuchtigkeitsSensor:  # Realisiert 'Messbar'
    def lese_wert(self) -> float:
        return 42.5

class TemperaturSensor:    # Realisiert 'Messbar'
    def lese_wert(self) -> float:
        return 21.0

UML-Beziehungen: Pfeile & Symbole im Überblick

Objekte arbeiten nicht isoliert, sondern stehen in präzisen Beziehungen zueinander.

Mermaid-Syntax Beziehung Kopplung Bedeutung & Faustregel
..> Abhängigkeit Sehr lose "Benutzt kurzzeitig" (Parameter, lokale Variable, erzeugt)
--> Assoziation Lose "Nutzt / Kennt" (unabhängige Lebenszyklen)
o-- Aggregation Mittel "Besteht aus" (Teile überleben das Ganze)
*-- Komposition Hoch "Besitzt existenziell" (Teile sterben mit dem Ganzen)
<|-- Vererbung Sehr hoch "Ist ein / Generalisierung" (starr zur Entwurfszeit)
<|.. Realisierung Minimal "Erfüllt Vertrag / Interface" (Polymorphie)

UML-Symbole: gestrichelter offener Pfeil · Linie (opt. offene Pfeilspitze = Navigierbarkeit) · weiße Raute · schwarze Raute · weißes Dreieck · gestrichelt + weißes Dreieck.

Multiplizitäten (Kardinalitäten)

Stehen an den Enden der Verbindungslinien:

  • 1 : Genau eins
  • 0..1 : Optional (null oder eins)
  • * oder 0..* : Beliebig viele (null bis unendlich)
  • 1..* : Mindestens eins bis unendlich
  • 2..5 : Fester Bereich von 2 bis 5

Vererbung verstehen (1/4): Das mentale Modell ("Ist-Ein")

Vererbung ist eines der bekanntesten Konzepte der OO – wird aber von Einsteigern oft missverstanden.

Was bedeutet Vererbung wirklich?

  • Generalisierung (Basisklasse / Superklasse):
    Gemeinsame Eigenschaften aller Pflanzen (z. B. name, preis) werden einmal zentral in Pflanze definiert.
  • Spezialisierung (Subklasse / Kindklasse):
    Eine Zimmerpflanze oder Gartenblume übernimmt automatisch alle Felder und Methoden der Pflanze und fügt nur ihre speziellen Besonderheiten hinzu.

Die "Ist-Ein"-Regel (Is-A):
Vererbung darf nur verwendet werden, wenn die Kindklasse logisch immer und überall ein vollwertiger Ersatz für die Elternklasse ist!
✅ Eine Zimmerpflanze ist eine Pflanze.
❌ Ein Blumentopf ist keine Pflanze – er enthält eine (→ Aggregation, die Pflanze überlebt das Umtopfen).

classDiagram class Pflanze { +name : String +preis : float +basisInfo() String } class Zimmerpflanze { +topfCm : int +topfInfo() String } class Gartenstrauch { +winterhart : bool } Pflanze <|-- Zimmerpflanze Pflanze <|-- Gartenstrauch

Die Vokabeln im Überblick:

  • Basisklasse (Elternklasse / Superklasse): Die allgemeinere Klasse oben in der Hierarchie.
  • Abgeleitete Klasse (Kindklasse / Subklasse): Die speziellere Klasse, die erbt und erweitert.

Vererbung verstehen (2/4): Attribute & der Konstruktor mit super()

Wie übernimmt die Kindklasse die Attribute der Basisklasse?
Hier lauert die häufigste Fehlerquelle für Python-Einsteiger!

Die goldene Regel für __init__:

Wenn eine Subklasse eine eigene __init__-Methode definiert, wird die __init__-Methode der Elternklasse nicht automatisch aufgerufen!

  • Ruft man super().__init__(...) nicht auf, existieren die Elternattribute im Kindobjekt schlichtweg nicht!
  • Zugriff auf self.name führt dann zur Laufzeit unweigerlich zum Absturz:
    AttributeError: 'Zimmerpflanze' object has no attribute 'name'!

Merksatz:
In der Regel ruft man super().__init__(...) gleich zu Beginn des Kind-Konstruktors auf, um die Basis-Attribute sauber zu initialisieren. (Python erzwingt die Position nicht – vorher dürfen z. B. Argumente aufbereitet werden.)

class Pflanze:
    def __init__(self, name: str, preis: float) -> None:
        self.name: str = name
        self.preis: float = preis

class Zimmerpflanze(Pflanze):
    def __init__(self, name: str, preis: float, topf_cm: int) -> None:
        # 1. Eltern-Konstruktor explizit aufrufen:
        super().__init__(name, preis)
        
        # 2. Eigene Attribute initialisieren:
        self.topf_cm: int = topf_cm

# Test:
zp = Zimmerpflanze("Monstera", 29.99, 19)
print(zp.name)     # "Monstera" (von Pflanze geerbt!)
print(zp.preis)    # 29.99 (von Pflanze geerbt!)
print(zp.topf_cm)  # 19 (aus Zimmerpflanze)

Vererbung verstehen (3/4): Methoden erben & überschreiben (Overriding)

Subklassen erben nicht nur Daten, sondern auch das Verhalten (Methoden) der Basisklasse.

1. Methoden direkt nutzen:

  • Alle Methoden der Basisklasse stehen der Subklasse automatisch zur Verfügung, ohne eine einzige Zeile Code zu schreiben.

2. Methoden überschreiben (Method Overriding):

  • Wenn eine Subklasse ein spezifischeres Verhalten benötigt, definiert sie eine Methode mit demselben Namen wie in der Basisklasse.
  • Python führt dann automatisch die Version der Subklasse aus.

3. Verhalten erweitern mit super().methode():

  • Oft will man die Elternlogik nicht komplett ersetzen, sondern nur anreichern.
  • super().methode() ruft die Original-Logik der Elternklasse auf.
class Pflanze:
    def __init__(self, name: str, preis: float) -> None:

Vererbung verstehen (4/4): Wann Vererbung hilft – und wann sie schadet

Vererbung klingt verlockend: "Ich spare mir Tipparbeit, indem ich von einer bestehenden Klasse erbe!"
Doch genau hier beginnt der schleichende Architektur-Verfall.

Wann Vererbung sinnvoll ist:

  • Es liegt eine echte, unveränderliche "Ist-Ein"-Beziehung vor.
  • Die Subklasse kann an jeder Stelle im Programm für die Basisklasse eingesetzt werden (Liskov-Substitutionsprinzip).
  • Die Hierarchie ist flach (maximal 1–2 Ebenen).

Wann Vererbung schadet:

  • Statisch & starr: Die Vererbungshierarchie wird zur Entwurfszeit festgelegt. Ein Wechsel der Elternklasse zur Laufzeit ist nicht vorgesehen!
  • White-Box-Wiederverwendung: Die Subklasse hängt von internen Details der Elternklasse ab.

Die typischen Anfänger-Fallen:

  1. "Code Reuse"-Falle:
    "Ich brauche nur die Methode speichern() aus DatenbankHandler, also erbe ich davon!"
    ❌ Falsch: Eine Pflanze ist kein DatenbankHandler! Nutze Komposition!
  2. Klassenexplosion:
    Sobald Objekte in mehreren Dimensionen variieren (Art, Topf, Sensor), explodiert die Anzahl der Klassen.
  3. Fragile Base Class:
    Eine winzige interne Optimierung in der Basisklasse bringt unbemerkt Subklassen zum Einsturz.

Design-Leitsatz:
"Favor object composition over class inheritance." (GoF)

Interfaces in Python: abc.ABC vs. typing.Protocol

Ein Interface (Schnittstelle) ist ein formaler Vertrag: Es legt fest, welche Methoden ein Objekt anbieten muss, ohne die Implementierung vorzugeben.

Python bietet zwei Wege, Schnittstellen zu definieren:

1. abc.ABC (Nominales Subtyping)

  • Explizite Vererbung: class StammkundenRabatt(RabattStrategie):
  • "Ich erfülle den Vertrag, weil ich explizit davon erbe."
  • Nachteil: Starke Kopplung, Modul-Abhängigkeit.

2. typing.Protocol (Strukturelles Subtyping)

  • Eingeführt in PEP 544 (Python 3.8): "Statisches Duck Typing".
  • "Wenn es wie eine Ente quakt und schwimmt, ist es eine Ente!"
  • Eine Klasse erfüllt das Protocol automatisch, sobald sie die Signaturen besitzt – völlig ohne Vererbung!
from typing import Protocol

# 1. Vertrag als Protocol definieren:
class RabattStrategie(Protocol):
    def berechne(self, basis: float) -> float: ...

# 2. Implementierung (KEIN 'class ...(RabattStrategie)'!):
# Die Klasse weiß überhaupt nichts vom Protocol!
class StammkundenRabatt:
    def berechne(self, basis: float) -> float:
        return basis * 0.85

# 3. Client nutzt das Protocol als Typ-Annotation:
def erstelle_rechnung(preis: float, r: RabattStrategie) -> None:
    endpreis = r.berechne(preis)
    print(f"Endpreis: {endpreis:.2f} €")

# ✅ Mypy und IDEs bestätigen: Passt perfekt!
erstelle_rechnung(100.0, StammkundenRabatt())

Einsatzbereiche und Architekturvorteile von typing.Protocol

1. Zero Coupling (Vollständige Entkopplung)

  • Die implementierende Klasse muss das Interface-Modul nicht importieren.
  • Hilft, zirkuläre Importe zwischen Modulen zu vermeiden.

2. Fremdbibliotheken integrieren

  • Klassen aus externen Paketen (requests, pandas, SQLAlchemy) können deine Protocols erfüllen, ohne deren Quellcode ändern zu müssen.
  • Bei abc.ABC nur über MeinABC.register(FremdeKlasse) möglich – und diese Registrierung erkennen statische Typchecker wie mypy nicht.

3. Müheloses Mocking & Unit-Testing

  • Für Tests genügt ein minimales Dummy-Objekt mit den geforderten Methoden.
  • Kein Zwang zu komplexen Mocking-Frameworks oder riesigen Vererbungshierarchien.

4. Consumer-Driven Interfaces (ISP)

  • Nicht der Anbieter bestimmt ein überladenes Riesen-Interface, sondern der Konsument fordert genau das Minimum an Methoden:
class HatFeuchtigkeit(Protocol):
    feuchtigkeit: int

def alarm_pruefen(sensor: HatFeuchtigkeit) -> bool:
    return sensor.feuchtigkeit < 20

⚠️ Wichtige Warnung: Keine Runtime-Checks in Python!

Wer von Sprachen wie Java, C# oder TypeScript kommt, erlebt in Python oft eine gefährliche Überraschung:

Python prüft Type Hints & Protocols NICHT zur Laufzeit!

  • Der Standard-Python-Interpreter (CPython) prüft Typ-Annotationen während der Programmausführung nicht! (Er speichert sie lediglich in __annotations__ – z. B. für @dataclass.)
  • Übergibst du an def erstelle_rechnung(preis: float, r: RabattStrategie) einen String oder ein falsches Objekt, akzeptiert Python das beim Aufruf anstandslos!
  • Der Absturz erfolgt erst mitten in der Funktion:
    AttributeError: 'str' object has no attribute 'berechne'!

Klartext:
Type Hints und Protocol sind Werkzeuge für die statische Code-Analyse (vor der Ausführung) – sie sind keine Sicherheitsgarantie zur Laufzeit!

Wie schützt man sich professionell?

  1. Statische Analyse in der CI/CD-Pipeline (Pflicht!):

    mypy src/ --strict

    Mypy prüft dein gesamtes Projekt vor dem Deployment und bricht bei Typfehlern den Build ab.

  2. Laufzeit-Validierung an Systemgrenzen:
    Kommen Daten von außen (HTTP-Requests, JSON-Dateien, Datenbanken)?
    Nutze Pydantic! Pydantic erzwingt Typ-Validierung zur Laufzeit und wirft verständliche Fehler.

  3. isinstance() bei Protocols (nur mit @runtime_checkable):

    from typing import Protocol, runtime_checkable

@runtime_checkable
class RabattStrategie(Protocol): ...

# Nun funktioniert: isinstance(obj, RabattStrategie)

    ⚠️ Prüft nur, ob die Methoden existieren – nicht deren Signaturen oder Typen!

Gefahr 1 der Vererbung: Die Klassenexplosion (Class Explosion)

Vererbung wird von Anfängern oft als Allzweckwaffe genutzt.
Das Problem: Reale Objekte besitzen viele voneinander unabhängige Eigenschaften (Dimensionen):

  • Dimension 1 (Pflanzenart): Zimmerpflanze, Balkonblume, Nutzpflanze (3 Varianten)
  • Dimension 2 (Gefäß): Keramiktopf, Tontopf, Pflanzbeutel (3 Varianten)
  • Dimension 3 (Sensorik): Mit IoT-Sensor, Ohne Sensor (2 Varianten)

Versucht man, diese Varianten durch Vererbung (is-a) abzubilden, multiplizieren sich die Möglichkeiten:
3 × 3 × 2 = 18 Klassen!
Kommt eine 4. Eigenschaft hinzu (z. B. B2B-Rabatt: ja/nein), sind es sofort 36 Klassen!

Die Kombinationsfalle im Klassendiagramm

Pflanze
 ├── Zimmerpflanze
 │    ├── ZimmerpflanzeMitSensor
 │    │    ├── ZimmerpflanzeSensorKeramik
 │    │    └── ZimmerpflanzeSensorTon
 │    └── ZimmerpflanzeOhneSensor ...
 └── Balkonblume
      ├── BalkonblumeMitSensor ...
      └── BalkonblumeOhneSensor ...

Das Fazit: Vererbung ist eindimensional hierarchisch. Unabhängige Eigenschaften führen unweigerlich zur Klassenexplosion und redundantem Code!

Gefahr 2 der Vererbung: Das Fragile Base Class Problem

Das Fragile Base Class Problem ist eine der tückischsten Schwachstellen der Objektorientierung.

Was bedeutet "Fragile" (zerbrechlich)?

  • Eine Subklasse hängt nicht nur von den Methodennamen der Basisklasse ab, sondern von deren interner Implementierung!
  • Eine scheinbar völlig unschuldige Optimierung oder Änderung in der Basisklasse bricht unbemerkt das Verhalten der Subklassen, obwohl alle Signaturen gleich bleiben!

Kernaussage:
"Inheritance breaks encapsulation!" (Vererbung durchbricht die Kapselung – Snyder 1986, aufgegriffen von der GoF).

Subklassen sind keine echten Black-Boxes, sondern eng an die interne Aufrufhierarchie der Elternklasse gekoppelt.

Wie entsteht die Falle? (Der Selbstaufruf)

  1. Die Basisklasse hat zwei Methoden:
    • hinzufuegen(element)
    • alle_hinzufuegen(liste)
  2. Intern ruft die Basisklasse alle_hinzufuegen() auf, indem sie in einer Schleife self.hinzufuegen() aufruft (Selbstaufruf).
  3. Eine Subklasse überschreibt nun beide Methoden, um Elemente zu zählen...

👉 Auf der nächsten Folie sehen wir, was nun Katastrophales passiert!

Die Selbstaufruf-Falle: Codebeispiel

Was Ada vorhatte:

(Klassisches Lehrbeispiel nach Joshua Bloch, Effective Java)
Ada möchte einen GezaehlterKatalog bauen, der stets mitzählt, wie viele Pflanzen jemals in den Katalog eingefügt wurden.

  • Sie überschreibt hinzufuegen(): gesamt += 1
  • Sie überschreibt alle_hinzufuegen(): gesamt += len(liste)
  • Danach ruft sie jeweils super() auf.

Das böse Erwachen:

  • Sie ruft alle_hinzufuegen(["Monstera", "Ficus", "Farne"]) mit 3 Pflanzen auf.
  • Der Zähler steht am Ende auf 6!
  • Warum? super().alle_hinzufuegen() ruft intern 3-mal self.hinzufuegen() auf – und das landet in Adas überschriebener Methode! Jedes Element wurde doppelt gezählt!
class PflanzenKatalog:
    def __init__(self):
        self._pflanzen: list[str] = []

    def hinzufuegen(self, p: str):
        self._pflanzen.append(p)

    def alle_hinzufuegen(self, liste: list[str]):
        for p in liste:
            self.hinzufuegen(p)  # ⚠️ Interner Selbstaufruf!

class GezaehlterKatalog(PflanzenKatalog):
    def __init__(self):
        super().__init__()
        self.gesamt = 0

    def hinzufuegen(self, p: str):
        self.gesamt += 1
        super().hinzufuegen(p)

    def alle_hinzufuegen(self, liste: list[str]):
        self.gesamt += len(liste)  # +3
        super().alle_hinzufuegen(liste) # Ruft 3x hinzufuegen()!

k = GezaehlterKatalog()
k.alle_hinzufuegen(["Monstera", "Ficus", "Farne"])
print(k.gesamt)  # 💥 6 statt 3!

Vererbung vs. Komposition: White-Box vs. Black-Box

❌ Vererbung = White-Box-Reuse

  • Die Subklasse muss die internen Selbstaufrufe und privaten Details der Basisklasse kennen.
  • Tight Coupling (Starke Kopplung): Ändert der Autor der Basisklasse später seine Implementierung (z. B. Verzicht auf die Hilfsmethode), bricht die Subklasse still und leise!
  • Starr zur Entwurfszeit: Die Elternklasse steht mit der Klassendefinition fest; ein Wechsel zur Laufzeit ist nicht vorgesehen.

✅ Komposition = Black-Box-Reuse

  • Klassen interagieren ausschließlich über die öffentliche Schnittstelle.
  • Wie die andere Klasse intern arbeitet, ist völlig egal – keine Selbstaufruf-Fallen!
  • Lose Kopplung: Änderungen an Implementierungsdetails bleiben streng isoliert.
  • Flexibel zur Laufzeit: Bausteine können jederzeit dynamisch ausgetauscht oder gewrappt werden.
Deshalb lautet das wichtigste Entwurfsprinzip der Gang of Four (GoF): 👉 "Favor object composition over class inheritance!"

Das Lösungsprinzip: Composition over Inheritance & Delegation

"Favor object composition over class inheritance."
(GoF, Design Patterns 1994)

Wie funktioniert Komposition in der Praxis?

  • "Has-A" statt "Is-A": Die Klasse erbt kein Verhalten, sondern besitzt eine Referenz auf ein eigenständiges Hilfsobjekt.
  • Delegation: Fachliche Methoden leiten Anfragen gezielt an das Komponentenobjekt weiter (self.sensor.ist_trocken()).
  • Echte Kapselung (Black-Box): Keine Selbstaufruf-Fallen oder Abhängigkeiten von Eltern-Interna!
  • Laufzeit-Flexibilität: Komponenten können im laufenden Betrieb beliebig ausgetauscht oder erweitert werden.

⚠️ Achtung Begriff: „Composition“ im GoF-Prinzip meint allgemein Objektkomposition (Zusammensetzen aus Teilobjekten). Das ist nicht identisch mit der UML-Komposition (schwarze Raute)! Der austauschbare Sensor im Beispiel wäre in UML eine Aggregation.

from dataclasses import dataclass

@dataclass
class BodenSensor:
    feuchtigkeit_prozent: int
    def ist_trocken(self) -> bool:
        return self.feuchtigkeit_prozent < 30

class Pflanze:
    def __init__(self, name: str, sensor: BodenSensor | None = None):
        self.name = name
        # Komposition: Pflanze BESITZT einen Sensor (has-a)
        self.sensor = sensor

    def muss_gegossen_werden(self) -> bool:
        if self.sensor is None:
            return False
        # DELEGATION: Leitet die Arbeit an die Komponente weiter!
        return self.sensor.ist_trocken()

# Laufzeit-Flexibilität ohne neue Klassen:
monstera = Pflanze("Monstera", sensor=BodenSensor(20))
print(monstera.muss_gegossen_werden())  # True (delegiert!)

# Sensor zur Laufzeit wechseln:
monstera.sensor = BodenSensor(55)
print(monstera.muss_gegossen_werden())  # False

Die SOLID-Prinzipien: Warum Softwaredesign?

Die SOLID-Prinzipien wurden von Robert C. Martin ("Uncle Bob") um 2000 zusammengestellt; das Akronym prägte Michael Feathers. Einzelne Prinzipien sind älter: OCP stammt von Bertrand Meyer (1988), LSP von Barbara Liskov (1987).
Sie sind der weltweite Standard für wartbaren, sauberen Objektentwurf.

  • S – Single Responsibility Principle (SRP)
  • O – Open/Closed Principle (OCP)
  • L – Liskov Substitution Principle (LSP)
  • I – Interface Segregation Principle (ISP)
  • D – Dependency Inversion Principle (DIP)

Ziel: Software soll gegen Anforderungen von morgen resistent sein, ohne dass bei jeder Änderung das Fundament einstürzt.

Die Symptome schlechter Software (nach R. C. Martin):

  1. Rigidity (Starrheit): Eine kleine Änderung zieht eine Kaskade weiterer Änderungen nach sich.
  2. Fragility (Zerbrechlichkeit): Eine Änderung an Modul A zerstört unbemerkt Funktionalität in Modul B.
  3. Immobility (Unbeweglichkeit): Code kann in neuen Teilen des Projekts nicht wiederverwendet werden, weil er zu stark verfilzt ist.
  4. Viscosity (Zähigkeit): Der „saubere“ Weg ist mühsamer als ein Hack – also wird gehackt.

Präzisere Fassung (R. C. Martin): "Ein Modul sollte gegenüber genau einem Akteur verantwortlich sein."

Eine Klasse Pflanze, die:

SOLID 2: Open/Closed Principle (OCP)

"Module sollten offen für Erweiterung, aber geschlossen für Modifikation sein."
(Bertrand Meyer, 1988)

  • Offen für Erweiterung: Neues Verhalten kann jederzeit ergänzt werden (z. B. neue Rabattarten).
  • Geschlossen für Modifikation: Bestehender, getesteter Code muss dafür nicht angefasst werden!
# ❌ Verstoß gegen OCP (ständiges Reineditieren nötig):
def berechne_alt(preis: float, typ: str) -> float:
    if typ == "standard":
        return preis
    elif typ == "b2b":
        return preis * 0.80
    # Jede neue Aktion erfordert Änderungen hier!

# ✅ Erfüllt OCP: Offen für neue Rabatte, Kerncode bleibt stabil!
from typing import Protocol

# 1. Gemeinsamer Vertrag (Abstraktion):
class RabattStrategie(Protocol):
    def berechne(self, preis: float) -> float: ...

# 2. Konkrete Strategien (beliebig erweiterbar):
class StandardRabatt:
    def berechne(self, preis: float) -> float: return preis

class B2BRabatt:
    def berechne(self, preis: float) -> float: return preis * 0.80

# 3. Client wendet die Strategie an (bleibt unangetastet!):
def berechne_endpreis(preis: float, rabatt: RabattStrategie) -> float:
    return rabatt.berechne(preis)

# 4. Anwendung im Programm:
print(berechne_endpreis(100.0, StandardRabatt()))  # 100.0
print(berechne_endpreis(100.0, B2BRabatt()))        # 80.0

SOLID 3: Liskov Substitution Principle (LSP)

"Subklassen müssen sich so verhalten, dass sie ihre Basisklasse ohne Überraschungen oder Fehler ersetzen können."

  • Benannt nach Computer-Pionierin Barbara Liskov.
  • Wenn ein Programm eine Pflanze erwartet, muss jede abgeleitete Subklasse funktionieren.
  • Klassischer Verstoß bei Ada:
    • Kunstpflanze erbt von Zimmerpflanze.
    • Ruft jemand pflanze.giesse(100) auf, wirft die Kunstpflanze einen RuntimeError("Ich bin aus Plastik!")!
    • ⇒ Das bricht den aufrufenden Code!
  • Lösung: Fähigkeiten getrennt modellieren – eine Kunstpflanze ist ein Artikel, aber nicht Giessbar.
# ❌ Verstoß gegen LSP:
class Zimmerpflanze:
    def giesse(self, ml: int) -> None:
        self.feuchtigkeit += ml

class Kunstpflanze(Zimmerpflanze):
    def giesse(self, ml: int) -> None:
        # Überraschung für den Aufrufer:
        raise RuntimeError("Ich bin aus Plastik!")

# ✅ Erfüllt LSP: Fähigkeiten getrennt modellieren
class Artikel(Protocol):
    name: str
    preis: float

class Giessbar(Protocol):
    def giesse(self, ml: int) -> None: ...

@dataclass
class EchtePflanze:      # erfüllt Artikel UND Giessbar
    name: str
    preis: float
    feuchtigkeit: int = 0
    def giesse(self, ml: int) -> None:
        self.feuchtigkeit += ml

@dataclass
class Kunstpflanze:      # erfüllt nur Artikel – kein giesse()
    name: str
    preis: float

SOLID 4: Interface Segregation Principle (ISP)

"Clients sollten nicht gezwungen sein, von Methoden abzuhängen, die sie gar nicht nutzen."

  • Fette Interfaces ("Fat Interfaces"):
    Eine Schnittstelle, die versucht, alles für jeden bereitzustellen (giessen(), umtopfen(), batterie_wechseln(), bluetooth_koppeln()).
  • Lösung:
    Lieber viele kleine, spezifische Interfaces als ein riesiges Alleskönner-Interface.
  • Eine Klasse kann mehrere kleine Interfaces gleichzeitig implementieren!
# ❌ Verstoß gegen ISP:

    def duenge(self): ...

    def wechsle_batterie(self): ...        # Nur IoT-Töpfe!

# ✅ Erfüllt ISP: Kleine, fokussierte Interfaces:
class Giessbar(Protocol):
    def giesse(self, ml: int) -> None: ...

class Sensorfaehig(Protocol):

SOLID 5: Dependency Inversion Principle (DIP)

"High-Level-Module dürfen nicht von Low-Level-Modulen abhängen. Beide müssen von Abstraktionen (Interfaces) abhängen."
"Abstraktionen dürfen nicht von Details abhängen. Details müssen von Abstraktionen abhängen."

  • High-Level: Die Geschäftslogik (BestellService – wie Bestellungen ablaufen).
  • Low-Level: Die technische Infrastruktur (PostgresDatabase, FileStorage).
  • Der Fehler: Der BestellService erzeugt direkt db = PostgresDatabase().

SOLID 5: DIP in der Praxis (Codebeispiel & Testbarkeit)

Dependency Injection (DI) als Schlüssel:

Statt dass BestellService seine Abhängigkeit intern mit PostgresRepo() selbst instanziiert, wird sie von außen über den Konstruktor hineingereicht (Inversion of Control).

# ❌ Schlecht (harte Kopplung an PostgreSQL):
class BadBestellService:
    def __init__(self) -> None:
        self.repo = PostgresRepo()  # Kaum testbar ohne echte DB!

Der unschätzbare Vorteil:

  • Entkopplung: Die Geschäftslogik weiß nichts von Datenbanktreibern oder SQL-Dialekten.
  • Mühelose Unit-Tests: Im Test übergeben wir ein InMemoryFakeRepo – der Test läuft in Millisekunden und ganz ohne Datenbank!
  • Begriff: Ein Fake ist eine vereinfachte, funktionierende Implementierung; ein Mock prüft zusätzlich, welche Aufrufe stattfanden (Meszaros, xUnit Test Patterns).
# ✅ Erfüllt DIP: Hängt ausschließlich von der Abstraktion ab!
from typing import Protocol

# 1. Abstraktion (Vertrag):
class BestellSpeicher(Protocol):
    def speichern(self, bestell_id: str, betrag: float) -> None: ...

# 2. High-Level-Modul nutzt Dependency Injection:
class BestellService:
    def __init__(self, repo: BestellSpeicher) -> None:
        self.repo = repo  # Dependency Injection!

    def bestellung_aufgeben(self, b_id: str, betrag: float) -> None:
        # Fachlogik validieren...
        self.repo.speichern(b_id, betrag)

Entwurfsmuster: Das Strategy Pattern

Das Strategy Pattern kapselt eine Familie austauschbarer Algorithmen in eigenständigen Objekten und macht sie zur Laufzeit beliebig wechselbar.

Die Akteure:

  1. Context (Kunde): Hält eine Referenz auf eine Strategie und delegiert die Arbeit an sie.
  2. Strategy (RabattStrategie): Das gemeinsame Interface.
  3. Concrete Strategies (StandardRabatt, TreueRabatt): Die eigentlichen Berechnungsregeln.

Ada kann dem Kunden zur Laufzeit jederzeit einen Treuerabatt zuweisen, ohne die Kundenklasse anzufassen!

Strategy Pattern: Codebeispiel & dynamischer Wechsel

Delegation statt Vererbung:

  • Der Kunde erbt nicht von verschiedenen Rabattklassen (class Stammkunde etc.).
  • Er besitzt eine Referenz auf ein Objekt, das RabattStrategie erfüllt (Composition over Inheritance).
  • In berechne_preis() delegiert er die Berechnung an self.strategie.berechne(...).

Dynamischer Wechsel zur Laufzeit:

  • Ein Stammkunde verliert seinen Status oder erhält eine Sonderaktion?
  • Einfach k.strategie = TreueRabatt() zuweisen – keine Neuerzeugung des Kundenobjekts, kein Datenverlust, keine starre Vererbung!
from typing import Protocol

class RabattStrategie(Protocol):
    def berechne(self, preis: float) -> float: ...

class StandardRabatt:
    def berechne(self, preis: float) -> float:
        return preis

class TreueRabatt:
    def berechne(self, preis: float) -> float:
        return round(preis * 0.90, 2)  # 10 % Treuerabatt

class Kunde:
    def __init__(self, name: str, strategie: RabattStrategie) -> None:
        self.name = name
        self.strategie = strategie  # Delegation

    def berechne_preis(self, basis: float) -> float:
        return self.strategie.berechne(basis)

# Anwendung:
k = Kunde("Ada", StandardRabatt())
print(k.berechne_preis(100.0))  # 100.0

# Strategiewechsel zur Laufzeit:
k.strategie = TreueRabatt()
print(k.berechne_preis(100.0))  # 90.0

Entwurfsmuster: Die Fabrikmethode (Factory)

Eine Fabrik (Factory) kapselt die Objekterzeugung. Der Aufrufer muss die internen Konstruktionsdetails, Fallbacks und Validierungen nicht kennen.

Warum Fabrikmethoden in Python unverzichtbar sind:

  1. Kein Konstruktor-Überladen:
    In Python kann es nur ein einziges __init__ geben!
  2. Aussagekräftige Namen (Named Constructors):
    Statt unklarer Parameter nutzt man sprechende Namen wie .aus_sensor_daten() oder .aus_katalog_json().
  3. Statische Fabrikmethode vs. GoF Factory Method:
    • Was bedeutet GoF? "Gang of Four" (Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides) – die Autoren des wegweisenden Standardwerks Design Patterns (1994).
    • Statische Fabrikmethode (Static Factory / Named Constructor): Eine Methode (@staticmethod/@classmethod) oder Funktion zur Objekterzeugung (in Python weit verbreitet – aber kein GoF-Muster!).
    • Klassisches GoF Factory Method Pattern: Ein abstraktes Interface zur Objekterzeugung, das von Subklassen polymorph überschrieben wird.

Statische Fabrikmethode: Codebeispiel

Erzeugung aus rohen Sensordaten:

  • IoT-Sensordaten kommen als unstrukturierte JSON/Dict-Payloads an (oft mit fehlenden Feldern oder falschen Typen).
  • Die PflanzenFactory bereinigt, validiert und setzt Default-Werte.
  • Der restliche Anwendungscode arbeitet ausschließlich mit validen SmartPlant-Objekten!
  • Der Client ruft einfach PflanzenFactory.aus_sensor_daten(event) auf – sauber, sicher, selbsterklärend.
  • Idiomatische Alternative: Als @classmethod direkt an der Klasse (SmartPlant.aus_sensor_daten(event) mit return cls(...)) – so wie datetime.fromtimestamp() oder dict.fromkeys().
from typing import Any

class PflanzenFactory:
    @staticmethod
    def aus_sensor_daten(payload: dict[str, Any]) -> SmartPlant:
        """Statische Fabrikmethode: Validiert & erzeugt SmartPlant"""
        name = payload.get("device_name", "Unbekannte Pflanze")
        try:
            feuchte = int(payload.get("soil_moisture", 50))
        except (TypeError, ValueError):
            raise ValueError("soil_moisture ist keine Zahl")
        if not 0 <= feuchte <= 100:
            raise ValueError(f"Ungültige Feuchtigkeit: {feuchte} %")
        return SmartPlant(
            botanischer_name=name,
            preis=0.0,
            ist_feuchtigkeit=feuchte
        )

# Nutzung im IoT-Service:
event = {"device_name": "Ficus-Laden-1", "soil_moisture": 28}
pflanze = PflanzenFactory.aus_sensor_daten(event)
print(pflanze.muss_gegossen_werden())  # True

Das GoF Factory Method Pattern: Polymorphe Erzeugung

"Definiere eine Schnittstelle zur Erzeugung eines Objekts, aber lass Unterklassen entscheiden, welche Klasse instanziiert wird."
(GoF, Design Patterns 1994)

Unterschied zur statischen Fabrikmethode:

  • Statische Fabrik (@staticmethod): Eine feste Hilfsmethode entscheidet, welches Objekt gebaut wird (z. B. Parser für JSON).
  • GoF Factory Method: Nutzt Vererbung & Polymorphie. Die Basisklasse legt den Arbeitsablauf fest, deklariert die Erzeugungsmethode aber abstrakt (erstelle_sensor()). Konkrete Subklassen entscheiden, welches Produkt erzeugt wird!

Anwendungsfall:

Frameworks und erweiterbare Architekturen, bei denen der Kern-Ablauf fix ist, Drittentwickler aber eigene Produkt-Typen einhängen dürfen.

from abc import ABC, abstractmethod
from typing import Protocol

class Sensor(Protocol):
    def lese_wert(self) -> float: ...

class BodenFeuchtigkeitsSensor:
    def lese_wert(self) -> float: return 42.5

class LuftTemperaturSensor:
    def lese_wert(self) -> float: return 21.0

# 1. Abstrakter Erzeuger mit Factory Method:
class MessStation(ABC):
    @abstractmethod
    def erstelle_sensor(self) -> Sensor:
        """Die eigentliche Factory Method!"""
        ...

    def erfasse_messung(self) -> float:
        # Fester Ablauf (Template Method) nutzt das erzeugte Produkt:
        sensor = self.erstelle_sensor()
        return sensor.lese_wert()

# 2. Subklassen bestimmen das konkrete Produkt:
class FeuchtigkeitsStation(MessStation):
    def erstelle_sensor(self) -> Sensor:
        return BodenFeuchtigkeitsSensor()

class TemperaturStation(MessStation):
    def erstelle_sensor(self) -> Sensor:
        return LuftTemperaturSensor()
