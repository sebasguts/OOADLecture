Das Problem: Querschneidende Belange

In jedem Softwaresystem gibt es zwei Arten von Code:

1. Fachlogik (Core Concerns)

  • Das eigentliche Geschäftsziel: "Bestellung aufgeben", "Pflanze gießen", "Lagerbestand prüfen".
  • Gehört klar in eine bestimmte Fachklasse (BestellService).

2. Querschneidende Belange (Cross-Cutting Concerns)

  • Aufgaben, die in fast jedem Modul gebraucht werden:
    • Logging & Audit-Trails
    • Caching von Datenbank-Abfragen
    • Performance-Messung
    • Sicherheits- & Authentifizierungsprüfungen
    • Fehlerbehandlung & Retries

Die Alltagsanalogie: Salz in der Küche

  • Ein Koch kocht Pasta, brät Steak oder backt Brot (das sind die Fachgerichte).
  • Aber in jedem einzelnen Gericht braucht er Salz, Pfeffer und eine saubere Arbeitsplatte.
  • Das Problem: Wenn das Würzen und Putzen 80 % der Rezeptbeschreibung ausmacht, geht das eigentliche Kochen unter!

Die Zwillingsprobleme: Tangling & Scattering

1. Code Tangling (Verfilzung)

Fachlicher Code wird von technischem Hilfscode überwuchert.
Die Kernlogik ist kaum noch erkennbar!

# ❌ Verfilzte Methode (Tangling):
def bestelle_pflanze(id: str, kunde: str):
    log.info("Start Bestellung")       # Logging
    t0 = time.time()                   # Timing
    if not auth.is_logged_in(kunde):   # Sicherheit
        raise AuthError()
    # 2 Zeilen eigentliche Fachlogik:
    item = db.get(id)
    order = db.create_order(item)
    
    cache.set(f"order:{order.id}", order) # Caching
    metrics.record("order_time", time.time() - t0)
    return order

2. Code Scattering (Verstreuung)

Derselbe Logging-, Caching- oder Sicherheits-Code ist redundant über 30 Klassen im ganzen Projekt verstreut.

  • Wartungs-Albtraum:
    Ändert sich das Logging-Format oder der Cache-Server, müssen alle 30 Klassen manuell angefasst werden!
  • Vergesslichkeit:
    Ein Entwickler vergisst in einer neuen Methode den Try-Catch-Block ⇒ System stürzt ab.

Die Lösung: Aspektorientierte Programmierung

Aspektorientierte Programmierung (AOP) trennt querschneidende Belange (Aspekte) sauber von der fachlichen Geschäftslogik.

  • Reiner Fachcode: Fachklassen kümmern sich zu 100 % um ihr Geschäftsziel.
  • Zentrale Definition: Jeder Aspekt (z. B. Logging, Caching) existiert genau einmal.
  • Automatisches Einweben: Das System fügt den Aspekt zur Laufzeit oder Übersetzungszeit vor/nach der Zielmethode ein.
  • In Python: Wir nutzen dafür das mächtige Sprachmittel der Decorators!

Aspekte im UML-Klassendiagramm modellieren

Das Entwurfs-Dilemma bei Aspekten:

Da ein Aspekt transparent agiert (Aufrufer und Fachklasse rufen ihn im Fachcode nicht explizit auf), ist er im klassischen Klassendiagramm schwer sichtbar!

Standard-Konvention im Softwareentwurf:

  1. Eigene Aspekt-Komponente: Wird als Klasse mit dem Stereotyp <<aspect>> dargestellt.
  2. Pointcuts & Advices als Operationen: Zeigt, wann der Aspekt eingreift (z. B. before(), around(joinpoint), after()).
  3. Explizite Abhängigkeitspfeile: Eine gestrichelte Abhängigkeit (..>) mit Stereotyp <<uses aspect>> zeigt, welche Fachmethode durch den Aspekt geschützt oder erweitert wird.

Python Decorators Schritt für Schritt

Ein Decorator ist eine Funktion, die eine andere Funktion als Parameter entgegennimmt, sie in eine Hülle ("Wrapper") einpackt und die erweiterte Funktion zurückgibt.

Der Aufbau eines Decorators:

  1. Äußere Funktion: Nimmt die Originalfunktion func entgegen.
  2. Innere Wrapper-Funktion:
    Führt Vorarbeiten aus, ruft func(*args, **kwargs) auf, führt Nacharbeiten aus und gibt das Ergebnis zurück.
  3. @functools.wraps:
    Bewahrt den ursprünglichen Funktionsnamen und den Docstring.
import time
from functools import wraps

def measure_time(func):
    """Zentraler Timing-Aspekt"""
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        # Aufruf der eigentlichen Fachfunktion:
        result = func(*args, **kwargs)
        dauer = time.perf_counter() - start
        print(f"⏱️ {func.__name__} brauchte {dauer:.4f}s")
        return result
    return wrapper

# Anwendung mit sauberer @-Syntax:
@measure_time
def berechne_inventurwert(pflanzen: list) -> float:
    time.sleep(0.1)  # Simuliere Arbeit
    return sum(p.preis for p in pflanzen)

Praxis-Aspekt: Resilienz mit @retry_with_backoff

In verteilten Systemen schlagen Netzwerkaufrufe (z. B. zur Großhändler-API oder zu IoT-Bodenfeuchtesensoren) gelegentlich fehl.

Statt in jeder Methode manuelle while-Schleifen und try-except-Blöcke zu schreiben, kapseln wir das Wiederholungsverhalten in einem wiederverwendbaren Decorator:

  • Fängt Netzwerkfehler (ConnectionError, TimeoutError) ab.
  • Wiederholt den Aufruf bis zu max_retries Mal.
  • Verdoppelt die Wartezeit nach jedem Versuch (exponentieller Backoff), um den überlasteten Server zu schonen.
import time
from functools import wraps

def retry_with_backoff(max_retries=3, delay=1.0):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            current_delay = delay
            for attempt in range(1, max_retries + 1):
                try:
                    return func(*args, **kwargs)
                except (ConnectionError, TimeoutError) as e:
                    if attempt == max_retries:
                        raise  # Letzter Versuch gescheitert!
                    print(f"⚠️ Versuch {attempt} fehlgeschlagen. "
                          f"Warte {current_delay}s...")
                    time.sleep(current_delay)
                    current_delay *= 2.0  # Exponentieller Backoff
        return wrapper
    return decorator

@retry_with_backoff(max_retries=3, delay=0.5)
def frage_grosshaendler_preis(art_nr: str) -> float:
    # Fachcode bleibt völlig frei von Retry-Schleifen!
    return api_client.get_price(art_nr)

Das Observer Pattern (Beobachter-Muster)

Das Problem enger Kopplung:

Wenn ein Kunde eine Bestellung aufgibt, müssen mehrere Module reagieren:

  • Das Lager muss die Ware reservieren.
  • Der Kurierdienst muss die Route planen.
  • Die Marketing-Abteilung muss Treuepunkte gutschreiben.

Wenn der BestellService all diese Klassen direkt importiert und aufruft, entsteht ein unentwirrbares Knäuel aus Abhängigkeiten!

Die Lösung: Der Radio-Sender

  • Das Subjekt (EventBus / Sender) ruft niemanden direkt an.
  • Es sendet lediglich eine Benachrichtigung: "Bestellung #42 wurde bezahlt!".
  • Beliebig viele Beobachter (Observer / Listener) abonnieren das Ereignis unabhängig voneinander.
  • Neue Listener (z. B. ein Statistik-Modul) können hinzugefügt werden, ohne den BestellService auch nur um eine Zeile zu ändern!

Implementierung: Ein typsicherer EventBus

classDiagram class EventBus { -dict _subscribers +subscribe(Type eventType, Callable handler) void +publish(Object event) void } class LagerListener { +onBestellung(BestellEvent e) void } class KurierListener { +onBestellung(BestellEvent e) void } EventBus --> LagerListener : benachrichtigt EventBus --> KurierListener : benachrichtigt 
from collections import defaultdict
from typing import Callable, Type, Any
from dataclasses import dataclass

@dataclass(frozen=True)
class BestellungPlatziert:
    bestell_nr: str
    gesamtbetrag: float

class EventBus:
    def __init__(self):
        self._subscribers: dict[Type, list[Callable]] = defaultdict(list)

    def subscribe(self, event_type: Type, handler: Callable[[Any], None]):
        self._subscribers[event_type].append(handler)

    def publish(self, event: Any):
        for handler in self._subscribers[type(event)]:
            handler(event)

# Nutzung:
bus = EventBus()
bus.subscribe(BestellungPlatziert, lambda e: print(f"📦 Lager packt: {e.bestell_nr}"))
bus.subscribe(BestellungPlatziert, lambda e: print(f"🚚 Kurier plant Tour für {e.bestell_nr}"))

bus.publish(BestellungPlatziert("BEST-101", 49.90))

Warum Funktionales Design? Der Mutability-Bug

In rein objektorientierten Programmen wird der Zustand von Objekten ständig im Speicher verändert (veränderlicher Zustand / Mutability).

Der gefürchtete "Aliasing-Bug":

  • Zwei Variablen verweisen im Arbeitsspeicher auf dasselbe Objekt.
  • Funktion A ändert den Zustand im Glauben, alleine damit zu arbeiten.
  • Funktion B stürzt später an völlig anderer Stelle ab, weil sich die Daten "von Geisterhand" verändert haben!
  • In nebenläufigen Systemen (Threads/Async) führt das zu katastrophalen Race Conditions.
# ❌ Der heimliche Mutability-Bug:
class Pflanze:
    def __init__(self, name: str, preis: float):
        self.name = name
        self.preis = preis

def wende_sonderrabatt_an(p: Pflanze):
    p.preis *= 0.5  # 💥 Verändert das Originalobjekt!

katalog_monstera = Pflanze("Monstera", 40.0)

# Kunde bekommt Rabatt berechnet:
wende_sonderrabatt_an(katalog_monstera)

# Böses Erwachen: Im Katalog kostet die Monstera 
# ab jetzt für ALLE Kunden nur noch 20.00 €!
print(katalog_monstera.preis)  # 20.0 (Unerwünschter Seiteneffekt!)

Was ist Funktionale Programmierung?

Der mathematische Funktionsbegriff:

In der Mathematik ist eine Funktion f eine eindeutige Zuordnung:

f: D → Z,   x ↦ f(x)
Jedem Element *x* aus der Definitionsmenge *D* wird **genau ein** Element *y* aus der Zielmenge *Z* zugeordnet.

Die Kernprinzipien im Code:

  • Deterministisch: Bei gleicher Eingabe x erhalten wir immer die gleiche Ausgabe y.
  • Seiteneffektfrei (Stateless): Eine Funktion verändert weder globale Variablen noch ihre übergebenen Argumente noch den Systemzustand.
  • Referenzielle Transparenz: Ein Funktionsaufruf f(x) kann jederzeit durch sein Ergebnis ersetzt werden, ohne das Programmverhalten zu ändern!

Gegenüberstellung: Methode vs. Pure Function

# ❌ Imperativ mit Seiteneffekt (Impure):
kontostand = 100.0

def buche_ab(betrag: float):
    global kontostand
    kontostand -= betrag  # Ändert globalen Zustand!

# ✅ Funktional ohne Seiteneffekt (Pure):
def berechne_neuen_stand(stand: float, 
                         betrag: float) -> float:
    # Verändert nichts, gibt nur neues Ergebnis zurück:
    return stand - betrag

neuer_stand = berechne_neuen_stand(kontostand, 30.0)

Wichtig für Anfänger: In der FP wird das Ergebnis einer Funktion immer als Rückgabewert weitergereicht, statt bestehende Variablen im Speicher zu überschreiben!

Pure Functions & Unveränderlichkeit (Immutability)

1. Pure Functions (Reine Funktionen)

  • Deterministisch: Gleicher Input erzeugt immer exakt denselben Output.
  • Keine Seiteneffekte (No Side Effects):
    Keine globalen Variablen ändern, keine Parameter manipulieren, keine Festplatten- oder Datenbankänderungen im Verborgenen.
  • Extrem einfach zu testen und parallel auszuführen!

2. Immutability (Unveränderlichkeit)

  • Ein Datenobjekt kann nach der Erstellung niemals modifiziert werden.
  • Bei Änderungen wird ein neues Objekt mit den neuen Werten erzeugt.
from dataclasses import dataclass, replace

# ✅ Unveränderliche Datenstruktur:
@dataclass(frozen=True)
class Pflanze:
    botanischer_name: str
    preis: float

# ✅ Reine Funktion (Pure Function):
def berechne_rabattierten_preis(p: Pflanze, faktor: float) -> Pflanze:
    # Original 'p' bleibt zu 100% unangetastet!
    return replace(p, preis=p.preis * faktor)

katalog_monstera = Pflanze("Monstera", 40.0)
angebots_monstera = berechne_rabattierten_preis(katalog_monstera, 0.5)

print(katalog_monstera.preis)   # 40.0 (Unverändert sicher!)
print(angebots_monstera.preis)  # 20.0 (Neues Objekt!)

Typen im Funktionalen Design: Primitive & Produkt-Typen

In der OOP modellieren wir die Welt über Klassen mit Methoden.
Im Funktionalen Design trennen wir Daten und Logik strikt: Daten sind reine Typen!

1. Primitive Typen (Basiselemente):

  • Typen beschreiben Wertemengen: int, float, str, bool.
  • Ein Wert gehört zu einem Typ (z. B. 42: int, "Monstera": str).

2. Produkt-Typen (Kartesisches Produkt A × B):

  • Das kartesische Produkt A × B ist die Menge aller Paare (a, b) mit a ∈ A und b ∈ B.
  • In der Programmierung: Ein Tupel oder Record mit fester Anzahl an Feldern verschiedener Typen.
  • Beispiel Ada's Blumenladen:
    BestellPosition = ArtikelId × Menge × Einzelpreis
    (str × int × float)

Produkt-Typen in modernem Python

from typing import NamedTuple

# Variante 1: Einfaches Tupel (ohne Feldnamen):
pos_tupel: tuple[str, int, float] = ("PFL-101", 3, 14.50)

# Variante 2: NamedTuple (typsicher & selbsterklärend):
class BestellPosition(NamedTuple):
    artikel_id: str
    menge: int
    einzelpreis: float

pos = BestellPosition("PFL-101", 3, 14.50)
print(pos.artikel_id)  # "PFL-101"
print(pos.menge * pos.einzelpreis)  # 43.50

# Unveränderlich (Immutable):
# pos.menge = 5  💥 AttributeError: can't set attribute!
  • Vorteil: Feste Struktur, kein verdecktes Überschreiben, direkte Destrukturierbarkeit!

Typen im Funktionalen Design: Union-Typen & Listen

Neben dem Produkt zweier Typen gibt es zwei weitere grundlegende Typkonstruktionen:

3. Union-Typen (Summen-Typen A ∪ B):

  • Ein Wert ist entweder vom Typ A oder vom Typ B.
  • Modelliert Alternativen und Varianten ohne Vererbungshierarchien!
  • Beispiel Ada's Blumenladen:
    Zahlungsart = Bar | Kreditkarte | Rechnung
    Rabatt = KeinRabatt | Prozent(float) | Gutschein(float)

4. Listen-Typen ([A] bzw. list[A]):

  • Eine Sequenz von beliebig vielen Werten desselben Typs A.
  • Unterschied Tupel vs. Liste:
    • Tupel (Produkt): Feste Länge, unterschiedliche Typen (heterogen).
    • Liste: Variable Länge, gleicher Typ (homogen).

Python-Syntax für Union & Listen

from dataclasses import dataclass

# Python 3.12+ (PEP 695 Type-Alias-Statement):
@dataclass(frozen=True)
class Bar: pass

@dataclass(frozen=True)
class Karte:
    kartennummer_hash: str

@dataclass(frozen=True)
class Rechnung:
    iban: str

# Summen-Typ (Union): Genau EINE dieser Ausprägungen!
type Zahlungsart = Bar | Karte | Rechnung

# Listen-Typ: Homogene Sequenz beliebiger Länge
type Warenkorb = list[BestellPosition]

bestellung: Warenkorb = [
    BestellPosition("PFL-101", 2, 12.0),
    BestellPosition("TOPF-05", 2, 5.0)
]
  • Vollständig typisiert, selbsterklärend und ideal für Pattern Matching!

Funktionstypen & Vollständigkeit

1. Die Notation von Funktionstypen:

In der funktionalen Modellierung schreiben wir:

Eingabetyp → Ausgabetyp
  • BestellPosition → float: Nimmt eine Position, berechnet deren Zeilenpreis.
  • (float × float) → float: Nimmt zwei Gleitkommazahlen, liefert eine Summe.
  • In Python: Callable[[BestellPosition], float].

2. Das Prinzip der Vollständigkeit:

In Aspekte.txt gilt: Eine Funktion muss für jede gültige Eingabe eine definierte Ausgabe liefern!

  • Imperativer Code wirft oft ungefangene Exceptions ⇒ Programm stürzt unvorhersehbar ab.
  • Funktionaler Code gibt stattdessen ein Ergebnistupel oder Result-Typ zurück:
    teile: (float × float) → (float × bool)

Vollständigkeit im Python-Code

from typing import Callable

# Typdefinition einer Berechnungsfunktion:
type PreisRechner = Callable[[BestellPosition], float]

berechne_zeile: PreisRechner = (
    lambda pos: pos.menge * pos.einzelpreis
)

# Sichere, vollständige Funktion ohne Crash:
def sichere_division(zaehler: float, 
                     nenner: float) -> tuple[float, bool]:
    if nenner == 0.0:
        return (0.0, False)  # Signal: Ungültig!
    return (zaehler / nenner, True)  # Signal: Erfolg!

ergebnis, ok = sichere_division(100.0, 0.0)
if not ok:
    print("⚠️ Ungültige Berechnung sicher abgefangen!")
  • Fehler werden Teil des Datentyps – keine heimlichen Abstürze!

Higher-Order Functions: Funktionen als Daten

In der Funktionalen Programmierung sind Funktionen First-Class Citizens:

  • Sie können wie normale Variablen übergeben werden.
  • Sie können als Rückgabewert einer anderen Funktion entstehen.

Was ist eine Higher-Order Function (HoF)?

Eine Funktion, die:

  1. Mindestens eine Funktion als Argument entgegennimmt, oder
  2. Eine neue Funktion als Ergebnis zurückgibt.

Der Funktionstyp einer HoF:

A → (B → C)
*"Nimmt ein Argument vom Typ A und liefert eine Funktion, die B auf C abbildet."*

Beispiel: Rabatt-Fabrik für Ada's Blumenladen

from typing import Callable

# HoF: Erzeugt eine spezialisierte Rabattfunktion:
def erstelle_rabatt_rechner(prozent: float) -> Callable[[float], float]:
    """Schließt 'prozent' in einer Closure ein"""
    def rabattiere(betrag: float) -> float:
        return betrag * (1.0 - prozent / 100.0)
    return rabattiere

# Wir erzeugen spezialisierte Funktionsdaten:
rabatt_stammkunde = erstelle_rabatt_rechner(10.0)
rabatt_vip = erstelle_rabatt_rechner(25.0)

# Jetzt wenden wir die Funktionsdaten an:
print(rabatt_stammkunde(100.0))  # 90.0 €
print(rabatt_vip(100.0))          # 75.0 €
  • Die innere Funktion "merkt" sich den Rabattsatz (Closure), ohne globale Variablen zu benötigen!

Currying & Partielle Applikation

Oft haben Funktionen mehrere Parameter. Wie vereinfacht man deren Wiederverwendung?

1. Partielle Applikation:

  • Man legt einen Teil der Parameter fest und erhält eine neue Funktion mit weniger Parametern.
  • In Python direkt über functools.partial verfügbar.

2. Currying (nach Haskell Curry):

  • Die mathematische Umformung einer Funktion mit mehreren Argumenten in eine Kette einstelliger Funktionen:
    (A₁ × A₂ → B)   ⟺   A₁ → (A₂ → B)
  • Statt f(x, y) ruft man f(x)(y) auf.
  • Ermöglicht extrem modulare Datenfluss-Pipelines!

from functools import partial

# Standard-Funktion mit 2 Parametern:
def berechne_brutto(steuersatz: float, netto: float) -> float:
    return round(netto * (1.0 + steuersatz), 2)

# 1. Partielle Applikation mit partial():
mwst_pflanzen = partial(berechne_brutto, 0.07)  # 7%
mwst_deko = partial(berechne_brutto, 0.19)      # 19%

print(mwst_pflanzen(20.0))  # 21.40 €
print(mwst_deko(20.0))      # 23.80 €

# 2. Curried-Syntax mit Lambdas:
curried_brutto = lambda satz: lambda netto: netto * (1.0 + satz)
print(curried_brutto(0.07)(20.0))  # 21.40 €

class BestellPosition(NamedTuple):
    art_nr: str
    menge: int

berechne_zeile = lambda p: p.menge * p.einzelpreis

def waehle_rabatt(k) -> Callable[[float], float]:
    if k[1] == "Stammkunde":

Funktionaler Datenfluss: Programme als Funktionsboxen

Statt Objekte kreuz und quer durch das System zu reichen und ihren Zustand zu manipulieren, betrachtet das Funktionale Design Programme als gerichtete Datenflüsse (Data Flow):

  1. Input: Ein Strom unstrukturierter Rohdaten kommt an.
  2. Funktionsboxen (Pipelines):

Pattern Matching: Das Gegenbeispiel (Anti-Pattern)

Warum altes if/elif isinstance fehleranfällig ist:

In älterem Python-Code oder prozeduralem Stil prüft man Typen oft über verschachtelte if isinstance(...)-Kaskaden:

  1. Kein automatisches Entpacken: Attribute müssen manuell ausgelesen und lokalen Variablen zugewiesen werden.
  2. Laufzeitfehler (AttributeError): Greift man versehentlich auf ein Attribut zu, das in einer Subklasse fehlt, stürzt das System zur Laufzeit ab!
  3. Schwer lesbare Schachtelung: Zusätzliche Bedingungen (Guards) erfordern tiefe if/else-Verschachtelungen.
  4. Fehlende Vollständigkeitsprüfung: Vergisst man einen neuen Event-Typ, fällt er stillschweigend durch!

❌ Anti-Pattern: Spaghetti aus isinstance & if

# Unübersichtlich, fehleranfällig und redundant:
def verarbeite_transaktion_alt(event):
    if isinstance(event, NormalerVerkauf):
        b = event.betrag
        print(f"Standardkauf über {b:.2f} € verbucht.")
        
    elif isinstance(event, ExpressLieferung):
        # Manuelles Entpacken aller Attribute:
        b = event.betrag
        k = event.kurier_id
        # Verschachtelte Bedingung:
        if getattr(event, "eilig", False):
            print(f"🚨 Prio-Express über {b:.2f} € an Kurier {k}!")
        else:
            print(f"📦 Standard-Kurier {k} beauftragt.")
            
    else:
        # Fällt stillschweigend durch, wenn vergessen!
        print("❌ Unbekanntes Event!")

Modernes Structural Pattern Matching (match/case)

Eingeführt in Python 3.10: Das mächtigste Werkzeug zur Datenzerlegung.

Warum viel besser als altes switch/case?

  • Prüft nicht nur Werte, sondern die Struktur und die Klassen von Objekten!
  • Automatisches Entpacken (Destructuring):
    Attribute werden direkt in lokale Variablen gebunden.
  • Guards (if ...):
    Zusätzliche Bedingungen direkt im Pattern prüfbar.
  • Ersetzt hässliche und fehleranfällige if isinstance(...) Kaskaden!
from dataclasses import dataclass

@dataclass
class NormalerVerkauf:
    betrag: float

@dataclass
class ExpressLieferung:
    betrag: float
    kurier_id: str
    eilig: bool

def verarbeite_transaktion(event):
    match event:
        case NormalerVerkauf(betrag=b):
            print(f"Standardkauf über {b:.2f} € verbucht.")
            
        case ExpressLieferung(betrag=b, kurier_id=k, eilig=True):
            print(f"🚨 Prio-Express über {b:.2f} € an Kurier {k}!")
            
        case ExpressLieferung(betrag=b, kurier_id=k, eilig=False):
            print(f"📦 Standard-Kurier {k} beauftragt.")
            
        case _:
            print("❌ Unbekanntes Event!")
