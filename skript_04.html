Das Problem: Querschneidende Belange

In jedem Softwaresystem gibt es zwei Arten von Code:

1. Fachlogik (Core Concerns)

  • Das eigentliche Geschäftsziel: "Bestellung aufgeben", "Pflanze gießen", "Lagerbestand prüfen".
  • Gehört klar in eine bestimmte Fachklasse (BestellService).

2. Querschneidende Belange (Cross-Cutting Concerns)

  • Aufgaben, die in fast jedem Modul gebraucht werden:
    • Logging & Audit-Trails
    • Caching von Datenbank-Abfragen
    • Performance-Messung
    • Sicherheits- & Authentifizierungsprüfungen
    • Fehlerbehandlung & Retries

Die Alltagsanalogie: Salz in der Küche

  • Ein Koch kocht Pasta, brät Steak oder backt Brot (das sind die Fachgerichte).
  • Aber in jedem einzelnen Gericht braucht er Salz, Pfeffer und eine saubere Arbeitsplatte.
  • Das Problem: Wenn das Würzen und Putzen 80 % der Rezeptbeschreibung ausmacht, geht das eigentliche Kochen unter!

Die Zwillingsprobleme: Tangling & Scattering

1. Code Tangling (Verfilzung)

Fachlicher Code wird von technischem Hilfscode überwuchert.
Die Kernlogik ist kaum noch erkennbar!

# ❌ Verfilzte Methode (Tangling):
def bestelle_pflanze(id: str, kunde: str):
    log.info("Start Bestellung")       # Logging
    t0 = time.time()                   # Timing
    if not auth.is_logged_in(kunde):   # Sicherheit
        raise AuthError()
    # 2 Zeilen eigentliche Fachlogik:
    item = db.get(id)
    order = db.create_order(item)
    
    cache.set(f"order:{order.id}", order) # Caching
    metrics.record("order_time", time.time() - t0)
    return order

2. Code Scattering (Verstreuung)

Derselbe Logging-, Caching- oder Sicherheits-Code ist redundant über 30 Klassen im ganzen Projekt verstreut.

  • Wartungs-Albtraum:
    Ändert sich das Logging-Format oder der Cache-Server, müssen alle 30 Klassen manuell angefasst werden!
  • Vergesslichkeit:
    Ein Entwickler vergisst in einer neuen Methode den Try-Catch-Block ⇒ System stürzt ab.

Die Lösung: Aspektorientierte Programmierung

Aspektorientierte Programmierung (AOP) trennt querschneidende Belange (Aspekte) sauber von der fachlichen Geschäftslogik.

  • Reiner Fachcode: Fachklassen kümmern sich zu 100 % um ihr Geschäftsziel.
  • Zentrale Definition: Jeder Aspekt (z. B. Logging, Caching) existiert genau einmal.
  • Automatisches Einweben: Das System fügt den Aspekt zur Laufzeit oder Übersetzungszeit vor/nach der Zielmethode ein.
  • In Python: Wir nutzen dafür das mächtige Sprachmittel der Decorators!

Aspekte im UML-Klassendiagramm modellieren

Das Entwurfs-Dilemma bei Aspekten:

Da ein Aspekt im Hintergrund agiert (die Fachklasse ruft ihn im eigenen Code gar nicht selbst auf), ist er im normalen Klassendiagramm leicht zu übersehen!

Fachbegriffe einfach erklärt:

  • Joinpoint (Einhängepunkt): Die konkrete Methode im Fachcode, bei der eingegriffen wird (z. B. erstelleBestellung).
  • Pointcut (Auswahlregel): Die Regel, welche Methoden überwacht werden sollen.
  • Advice (Zusatzaktion): Was und wann der Aspekt etwas tut (before = vorher, after = nachher, around = drumherum).
  • UML-Notation: Wir kennzeichnen Aspekt-Klassen mit <<aspect>> und zeichnen einen gestrichelten Pfeil <<uses aspect>>.

Vorwissen für Decorators: Funktionen sind in Python normale Objekte!

Bevor wir verstehen können, wie ein @decorator funktioniert, müssen wir eine besondere Eigenschaft von Python kennenlernen:

First-Class Citizens (Bürger erster Klasse):
In Python sind Funktionen keine starren Befehle, sondern ganz normale Objekte – genau wie Zahlen (42), Texte ("Hallo") oder Listen!

Was bedeutet das konkret?

  1. Mit Klammern sag_hallo():
    Die Funktion wird sofort ausgeführt; wir erhalten ihr Ergebnis (den Rückgabewert).
  2. Ohne Klammern sag_hallo:
    Die Funktion wird nicht ausgeführt, sondern wie ein Paket als Wert in einer Variable gespeichert oder an eine andere Funktion übergeben!

Schritt-für-Schritt im Code:

def begruessung(name: str) -> str:
    return f"Willkommen bei Ada, {name}!"

# 1. Funktion OHNE () einer Variable zuweisen:
meine_aktion = begruessung
print(meine_aktion("Max"))  # "Willkommen bei Ada, Max!"

# 2. Funktion als Parameter an andere Funktion übergeben:
def fuehre_mit_log_aus(funktions_objekt, kunde: str):
    print(f"📢 Starte Funktion: {funktions_objekt.__name__}")
    ergebnis = funktions_objekt(kunde)  # Hier erst Aufruf mit ()!
    print("✅ Fertig!")
    return ergebnis

# Wir übergeben 'begruessung' OHNE Klammern:
fuehre_mit_log_aus(begruessung, "Anna")
  • Genau dieses Prinzip nutzen Decorators: Sie nehmen eine Funktion entgegen und bauen eine schützende Hülle darum!

Python Decorators Schritt für Schritt (Das Zwiebelschalen-Prinzip)

Ein Decorator ist eine Funktion, die eine andere Funktion (func) entgegennimmt, sie in eine Hülle (Wrapper = Geschenkpapier / Zwiebelschale) einpackt und die verpackte Funktion zurückgibt.

Was passiert im Hintergrund?

  • Die Schreibweise @measure_time über einer Funktion ist nur eine elegante Abkürzung (Syntactic Sugar) für:
    berechne = measure_time(berechne)
  • *args, **kwargs:
    Bedeutet: "Nimm beliebig viele Parameter entgegen und reiche sie unverändert an die Originalfunktion weiter."
  • @wraps(func):
    Sorgt dafür, dass die verpackte Funktion ihren echten Namen und Docstring behält.
import time
from functools import wraps

def measure_time(func):
    """Zentraler Timing-Aspekt (Die äußere Zwiebelschale)"""
    @wraps(func)
    def wrapper(*args, **kwargs):
        # 1. VORHER (Before-Advice): Stoppuhr starten
        start = time.perf_counter()
        
        # 2. ORIGINAL-FUNKTION aufrufen:
        result = func(*args, **kwargs)
        
        # 3. NACHHER (After-Advice): Zeit messen
        dauer = time.perf_counter() - start
        print(f"⏱️ {func.__name__} brauchte {dauer:.4f}s")
        return result
    return wrapper

# Anwendung mit sauberer @-Syntax:
@measure_time
def berechne_inventurwert(preise_cent: list[int]) -> int:
    time.sleep(0.1)  # Simuliere Arbeit
    return sum(preise_cent)

Praxis-Aspekt: Resilienz mit @retry_with_backoff

In echten Systemen schlagen Netzwerkaufrufe (z. B. zur Großhändler-API oder zu WLAN-Bodenfeuchtesensoren) manchmal kurzzeitig fehl.

Zwei wichtige Fachbegriffe:

  • Resilienz (Widerstandsfähigkeit):
    Die Fähigkeit eines Systems, bei Teilausfällen nicht sofort abzustürzen, sondern sich selbst zu erholen.
  • Exponential Backoff (Exponentielles Abwarten):
    Wenn ein Server überlastet ist, bombardieren wir ihn nicht im Millisekundentakt weiter! Wir verdoppeln nach jedem Fehlversuch die Pause (z. B. 1 s → 2 s → 4 s), damit sich der Server erholen kann.

(Da dieser Decorator eigene Parameter wie max_retries=3 annimmt, hat er eine äußere Konfigurations-Schale um den Decorator.)

import time
from functools import wraps

def retry_with_backoff(max_retries=3, delay=1.0):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            current_delay = delay
            for attempt in range(1, max_retries + 1):
                try:
                    return func(*args, **kwargs)
                except (ConnectionError, TimeoutError):
                    if attempt == max_retries:
                        raise  # Letzter Versuch gescheitert!
                    print(f"⚠️ Versuch {attempt} fehlgeschlagen. "
                          f"Warte {current_delay}s...")
                    time.sleep(current_delay)
                    current_delay *= 2.0  # Wartezeit verdoppeln!
        return wrapper
    return decorator

@retry_with_backoff(max_retries=3, delay=0.5)
def frage_grosshaendler_preis(art_nr: str) -> int:
    # Fachcode bleibt zu 100 % frei von Retry-Schleifen!
    return api_client.get_price_cents(art_nr)

Das Observer Pattern: Module entkoppeln (Brücke zu Modul 3)

Rückblick auf Modul 3 (Bounded Contexts):

Wir haben Adas System in getrennte Packages aufgeteilt: verkauf, lager und logistik.

Das Problem bei direktem Aufruf:

Wenn eine Bestellung bezahlt wird, müssen lager (Ware reservieren) und logistik (Kurier planen) reagieren.

  • Importiert der BestellService (in verkauf) nun direkt den LagerService und KurierService, entsteht wieder starke Kopplung!
  • Kommt morgen ein RechnungsService hinzu, müssen wir den BestellService schon wieder umbauen (Verstoß gegen das Open-Closed-Prinzip aus Modul 1!).

Die Lösung: Das Radio-Sender-Prinzip (Observer)

  • Der BestellService (Sender / Publisher) ruft niemanden direkt auf.
  • Er sendet eine Nachricht in einen neutralen EventBus (im common-Modul):
    "Ereignis: Bestellung #101 wurde platziert!"
  • Beliebig viele Beobachter (Observer / Subscriber) aus anderen Modulen hören diese Frequenz und reagieren selbstständig.
  • Vorteil: verkauf kennt weder lager noch logistik!

Implementierung: Ein typsicherer EventBus

classDiagram class EventBus { -dict _subscribers +subscribe(Type eventType, Callable handler) void +publish(Object event) void } class LagerListener { +onBestellung(BestellEvent e) void } class KurierListener { +onBestellung(BestellEvent e) void } EventBus --> LagerListener : benachrichtigt EventBus --> KurierListener : benachrichtigt 
from collections import defaultdict
from typing import Callable, Type, Any
from dataclasses import dataclass

@dataclass(frozen=True)
class BestellungPlatziert:
    bestell_nr: str
    gesamtbetrag: float

class EventBus:
    def __init__(self):
        self._subscribers: dict[Type, list[Callable]] = defaultdict(list)

    def subscribe(self, event_type: Type, handler: Callable[[Any], None]):
        self._subscribers[event_type].append(handler)

    def publish(self, event: Any):
        for handler in self._subscribers[type(event)]:
            handler(event)

# Nutzung:
bus = EventBus()
bus.subscribe(BestellungPlatziert, lambda e: print(f"📦 Lager packt: {e.bestell_nr}"))
bus.subscribe(BestellungPlatziert, lambda e: print(f"🚚 Kurier plant Tour für {e.bestell_nr}"))

bus.publish(BestellungPlatziert("BEST-101", 49.90))

Warum Funktionales Design? Der Mutability-Bug

In rein objektorientierten Programmen wird der Zustand von Objekten ständig im Speicher verändert (veränderlicher Zustand / Mutability).

Der gefürchtete "Aliasing-Bug":

  • Zwei Variablen verweisen im Arbeitsspeicher auf dasselbe Objekt.
  • Funktion A ändert den Zustand im Glauben, alleine damit zu arbeiten.
  • Funktion B stürzt später an völlig anderer Stelle ab, weil sich die Daten "von Geisterhand" verändert haben!
  • In nebenläufigen Systemen (Threads/Async) führt das zu katastrophalen Race Conditions.
# ❌ Der heimliche Mutability-Bug:
class Pflanze:
    def __init__(self, name: str, preis: float):
        self.name = name
        self.preis = preis

def wende_sonderrabatt_an(p: Pflanze):
    p.preis *= 0.5  # 💥 Verändert das Originalobjekt!

katalog_monstera = Pflanze("Monstera", 40.0)

# Kunde bekommt Rabatt berechnet:
wende_sonderrabatt_an(katalog_monstera)

# Böses Erwachen: Im Katalog kostet die Monstera 
# ab jetzt für ALLE Kunden nur noch 20.00 €!
print(katalog_monstera.preis)  # 20.0 (Unerwünschter Seiteneffekt!)

Was ist Funktionale Programmierung?

Der mathematische Funktionsbegriff einfach erklärt:

In der Mathematik ist eine Funktion f wie eine verlässliche Maschine:

f: D → Z,   x ↦ f(x)
Für jede **Eingabe** *x* (aus der Eingabemenge *D*) kommt **garantiert immer dieselbe Ausgabe** *y* (aus der Zielmenge *Z*) heraus.

Die 3 Kernprinzipien im Code:

  • Deterministisch: Gleiche Eingabe → immer exakt gleiche Ausgabe.
  • Seiteneffektfrei (Stateless): Die Funktion ändert heimlich nichts im Hintergrund (keine globalen Variablen, keine übergebenen Objekte).
  • Ersetzbarkeit (Referenzielle Transparenz): Man kann den Aufruf f(x) überall durch sein Ergebnis ersetzen, ohne dass sich das Programm anders verhält!

Gegenüberstellung: Seiteneffekt vs. Pure Function

# ❌ Imperativ mit Seiteneffekt (Impure):
kontostand = 100.0

def buche_ab(betrag: float):
    global kontostand
    kontostand -= betrag  # Ändert globalen Zustand!

# ✅ Funktional ohne Seiteneffekt (Pure):
def berechne_neuen_stand(stand: float, 
                         betrag: float) -> float:
    # Verändert nichts, gibt nur neues Ergebnis zurück:
    return stand - betrag

neuer_stand = berechne_neuen_stand(kontostand, 30.0)

Wichtig für Anfänger: In der FP wird das Ergebnis immer als Rückgabewert (return) weitergereicht, statt bestehende Variablen im Speicher zu überschreiben! (Hinweis: Für kompakte FP-Formeln nutzen wir hier float, in echten Kassensystemen Geldbetrag mit cent: int aus Modul 2.)

Pure Functions & Unveränderlichkeit (Immutability)

1. Pure Functions (Reine Funktionen)

  • Deterministisch: Gleicher Input erzeugt immer exakt denselben Output.
  • Keine Seiteneffekte (No Side Effects):
    Keine globalen Variablen ändern, keine Parameter manipulieren, keine Festplatten- oder Datenbankänderungen im Verborgenen.
  • Extrem einfach zu testen (assert fn(x) == y) und parallel auszuführen!

2. Immutability (Unveränderlichkeit)

  • Ein Datenobjekt ist wie ein ausgedruckter Kassenbon: Nach der Erstellung kann er niemals überschrieben werden (@dataclass(frozen=True)).
  • Bei einer Preisänderung wird mit replace() ein neues Objekt erzeugt – das Original im Katalog bleibt geschützt!
from dataclasses import dataclass, replace

# ✅ Unveränderliche Datenstruktur (frozen=True):
@dataclass(frozen=True)
class Pflanze:
    botanischer_name: str
    preis: float

# ✅ Reine Funktion (Pure Function):
def berechne_rabattierten_preis(p: Pflanze, faktor: float) -> Pflanze:
    # Original 'p' bleibt zu 100% unangetastet!
    return replace(p, preis=p.preis * faktor)

katalog_monstera = Pflanze("Monstera", 40.0)
angebots_monstera = berechne_rabattierten_preis(katalog_monstera, 0.5)

print(katalog_monstera.preis)   # 40.0 (Unverändert sicher!)
print(angebots_monstera.preis)  # 20.0 (Neues Objekt!)

Typen im Funktionalen Design: Primitive & Produkt-Typen ("UND-Kombination")

In der OOP stecken Daten und Methoden gemeinsam in Klassen.
Im Funktionalen Design trennen wir strikt: Daten sind reine, unveränderliche Strukturen!

1. Primitive Typen (Grundbausteine):

  • Einfache Einzelwerte: int (Ganzzahl), float (Kommazahl), str (Text), bool (Wahrheitswert).

2. Produkt-Typen (Die "UND-Kombination", A × B):

  • Warum heißt das Produkt-Typ (A × B)? Weil ein Datensatz Feld A UND Feld B UND Feld C gleichzeitig enthält (wie ein ausgefülltes Formular).
  • In Python nutzen wir dafür ein Tupel oder noch besser ein NamedTuple (ein unveränderliches Tupel mit sprechenden Feldnamen):
    BestellPosition = ArtikelId UND Menge UND Einzelpreis
    (str × int × float)

Produkt-Typen in modernem Python

from typing import NamedTuple

# Variante 1: Einfaches Tupel (ohne Feldnamen):
pos_tupel: tuple[str, int, float] = ("PFL-101", 3, 14.50)

# Variante 2: NamedTuple (typsicher & selbsterklärend):
class BestellPosition(NamedTuple):
    artikel_id: str
    menge: int
    einzelpreis: float

pos = BestellPosition("PFL-101", 3, 14.50)
print(pos.artikel_id)               # "PFL-101"
print(pos.menge * pos.einzelpreis)  # 43.50

# Automatisch unveränderlich (Immutable):
# pos.menge = 5  💥 AttributeError: can't set attribute!
  • Vorteil: Feste Struktur, kein heimliches Überschreiben!

Typen im Funktionalen Design: Union-Typen ("ODER-Auswahl") & Listen

Neben der "UND-Kombination" (Produkt-Typ) brauchen wir noch zwei weitere Werkzeuge:

3. Union-Typen (Die "ENTWEDER-ODER-Auswahl", A | B):

  • Ein Wert ist entweder vom Typ A oder vom Typ B (in Python mit dem Oder-Strich | geschrieben).
  • Modelliert verschiedene Varianten ganz ohne komplizierte Vererbung!
  • Beispiel Ada's Blumenladen:
    Zahlungsart = Bar | Karte | Rechnung
    Rabatt = KeinRabatt | Prozent(float) | Gutschein(float)

4. Listen-Typen (list[A]):

  • Beliebig viele Elemente desselben Typs A.
  • Merksatz für Anfänger:
    • Tupel (NamedTuple): Feste Felder verschiedener Typen (z. B. str, int, float).
    • Liste (list): Beliebig viele Einträge desselben Typs (z. B. 10 Bestellpositionen).

Python-Syntax für Union (|) & Listen

from dataclasses import dataclass

@dataclass(frozen=True)
class Bar: pass

@dataclass(frozen=True)
class Karte:
    kartennummer_hash: str

@dataclass(frozen=True)
class Rechnung:
    iban: str

# Union-Typ (ENTWEDER Bar ODER Karte ODER Rechnung):
type Zahlungsart = Bar | Karte | Rechnung

# Listen-Typ: Beliebig viele BestellPositionen
type Warenkorb = list[BestellPosition]

bestellung: Warenkorb = [
    BestellPosition("PFL-101", 2, 12.0),
    BestellPosition("TOPF-05", 2, 5.0)
]
  • Vollständig typisiert und ideal für match/case!

Funktionstypen & Totale Funktionen (Vollständigkeit)

1. Wie liest man einen Funktionstyp?

Im Funktionalen Design beschreibt der Pfeil →, was in eine Funktion hineingeht und was herauskommt:

Eingabetyp → Ausgabetyp
  • BestellPosition → float: Nimmt eine Position, liefert den Zeilenpreis.
  • In Python schreiben wir dafür: Callable[[BestellPosition], float].

2. Das Prinzip der Vollständigkeit (Totale Funktionen):

Eine Funktion heißt vollständig (total), wenn sie für jede mögliche Eingabe eine reguläre Ausgabe liefert – statt mitten im Betrieb mit einer Exception abzustürzen!

  • Statt bei Fehlern zu crashen, gibt die Funktion ein Ergebnistupel (Wert, Erfolg) oder einen Union-Typ Ergebnis | Fehler zurück:
    sichere_division: (float × float) → (float × bool)

Vollständigkeit im Python-Code

from typing import Callable

# Typdefinition: Nimmt BestellPosition, liefert float
type PreisRechner = Callable[[BestellPosition], float]

berechne_zeile: PreisRechner = (
    lambda pos: pos.menge * pos.einzelpreis
)

# Sichere, vollständige Funktion ohne Programmabsturz:
def sichere_division(zaehler: float, 
                     nenner: float) -> tuple[float, bool]:
    if nenner == 0.0:
        return (0.0, False)  # Signal: Ungültig!
    return (zaehler / nenner, True)  # Signal: Erfolg!

ergebnis, ok = sichere_division(100.0, 0.0)
if not ok:
    print("⚠️ Ungültige Berechnung sicher abgefangen!")
  • Der Aufrufer sieht schon am Rückgabetyp, dass etwas schiefgehen kann!

Higher-Order Functions: Funktionen als "Funktions-Fabrik"

Da Funktionen in Python normale Objekte (First-Class Citizens) sind, können wir Funktionen bauen, die mit anderen Funktionen arbeiten!

Was ist eine Higher-Order Function (Funktion höherer Ordnung)?

Eine Funktion heißt Higher-Order Function (HoF), wenn sie:

  1. Eine andere Funktion als Parameter annimmt (wie unser Decorator oder map), oder
  2. Eine neue Funktion herstellt und zurückgibt (wie eine Funktions-Fabrik).

Was ist eine Closure ("Funktion mit Rucksack")?

prozent: float → (betrag: float → float)
Wenn unsere Fabrik eine neue Funktion baut, packt sie die Konfiguration (z. B. `prozent = 10.0`) wie in einen unsichtbaren **Rucksack (Closure)** direkt in die erzeugte Funktion hinein!

Beispiel: Die Rabatt-Fabrik für Ada's Blumenladen

from typing import Callable

# HoF (Funktions-Fabrik): Baut eine fertige Rabattfunktion!
def erstelle_rabatt_rechner(prozent: float) -> Callable[[float], float]:
    """Packt 'prozent' in den Rucksack (Closure) der inneren Funktion"""
    def rabattiere(betrag: float) -> float:
        return betrag * (1.0 - prozent / 100.0)
    return rabattiere  # Gibt die Funktion OHNE () zurück!

# 1. Wir produzieren zwei maßgeschneiderte Funktionen:
rabatt_stammkunde = erstelle_rabatt_rechner(10.0)
rabatt_vip = erstelle_rabatt_rechner(25.0)

# 2. Später im Kassensystem wenden wir sie einfach an:
print(rabatt_stammkunde(100.0))  # 90.0 € (weiß noch: 10%!)
print(rabatt_vip(100.0))          # 75.0 € (weiß noch: 25%!)
  • rabatt_stammkunde erinnert sich dank Closure immer an seine 10.0 %!

Currying & Partielle Applikation ("Parameter vor-ausfüllen")

Oft hat man eine allgemeine Funktion mit mehreren Parametern (z. B. berechne_brutto(steuersatz, netto)), möchte aber einen Parameter fest voreinstellen:

1. Partielle Applikation ("Vor-Ausfüllen" mit partial):

  • Wie bei einem Überweisungsformular, in das der Empfänger schon fest eingedruckt ist: Man legt das erste Argument fest (z. B. steuersatz = 0.07) und erhält eine neue, einfachere Funktion, die nur noch den netto-Betrag braucht.

2. Currying (nach dem Mathematiker Haskell Curry):

  • Eine Funktion mit 2 Parametern wird so geschrieben, dass sie die Parameter nacheinander einzeln entgegennimmt:
    (Steuersatz × Netto → Brutto)   ⟺   Steuersatz → (Netto → Brutto)
  • Statt f(0.07, 20.0) kann man f(0.07) aufrufen, um einen Steuerrechner zu erhalten!

Praxis: Steuersätze im Blumenladen voreinstellen

from functools import partial

# Allgemeine Funktion mit 2 Parametern:
def berechne_brutto(steuersatz: float, netto: float) -> float:
    return round(netto * (1.0 + steuersatz), 2)

# 1. Partielle Applikation (Steuersatz fest voreinstellen):
mwst_pflanzen = partial(berechne_brutto, 0.07)  # 7% für Pflanzen
mwst_deko = partial(berechne_brutto, 0.19)      # 19% für Übertöpfe

# Im Kassen-Code brauchen wir nur noch den Netto-Preis übergeben:
print(mwst_pflanzen(20.0))  # 21.40 €
print(mwst_deko(20.0))      # 23.80 €

# 2. Zum Vergleich als Curried-Funktion:
curried_brutto = lambda satz: lambda netto: round(netto * (1.0 + satz), 2)
print(curried_brutto(0.07)(20.0))  # 21.40 €
  • Ideal, um Funktionen passgenau für Daten-Pipelines (map) vorzubereiten!

Funktionaler Datenfluss: Programme als Funktionsboxen

Statt Objekte kreuz und quer durch das System zu reichen und ihren Zustand zu manipulieren, betrachtet das Funktionale Design Programme als gerichtete Datenflüsse (Data Flow):

  1. Input: Ein Strom unstrukturierter Rohdaten kommt an.
  2. Funktionsboxen (Pipelines):

Jede Box kann unabhängig getestet, ausgetauscht oder parallelisiert werden!

Pattern Matching: Das Gegenbeispiel (Anti-Pattern)

Warum altes if/elif isinstance fehleranfällig ist:

In älterem Python-Code oder prozeduralem Stil prüft man Typen oft über verschachtelte if isinstance(...)-Kaskaden:

  1. Kein automatisches Entpacken: Attribute müssen manuell ausgelesen und lokalen Variablen zugewiesen werden.
  2. Laufzeitfehler (AttributeError): Greift man versehentlich auf ein Attribut zu, das in einer Subklasse fehlt, stürzt das System zur Laufzeit ab!
  3. Schwer lesbare Schachtelung: Zusätzliche Bedingungen (Guards) erfordern tiefe if/else-Verschachtelungen.
  4. Fehlende Vollständigkeitsprüfung: Vergisst man einen neuen Event-Typ, fällt er stillschweigend durch!

❌ Anti-Pattern: Spaghetti aus isinstance & if

# Unübersichtlich, fehleranfällig und redundant:
def verarbeite_transaktion_alt(event):
    if isinstance(event, NormalerVerkauf):
        b = event.betrag
        print(f"Standardkauf über {b:.2f} € verbucht.")
        
    elif isinstance(event, ExpressLieferung):
        # Manuelles Entpacken aller Attribute:
        b = event.betrag
        k = event.kurier_id
        # Verschachtelte Bedingung:
        if getattr(event, "eilig", False):
            print(f"🚨 Prio-Express über {b:.2f} € an Kurier {k}!")
        else:
            print(f"📦 Standard-Kurier {k} beauftragt.")
            
    else:
        # Fällt stillschweigend durch, wenn vergessen!
        print("❌ Unbekanntes Event!")

Modernes Structural Pattern Matching (match/case)

Eingeführt in Python 3.10: Das mächtigste Werkzeug zur Datenzerlegung.

Warum viel besser als altes switch/case?

  • Prüft nicht nur Werte, sondern die Struktur und die Klassen von Objekten!
  • Automatisches Entpacken (Destructuring):
    Attribute werden direkt in lokale Variablen gebunden.
  • Guards (if ...):
    Zusätzliche Bedingungen direkt im Pattern prüfbar.
  • Ersetzt hässliche und fehleranfällige if isinstance(...) Kaskaden!
from dataclasses import dataclass

@dataclass
class NormalerVerkauf:
    betrag: float

@dataclass
class ExpressLieferung:
    betrag: float
    kurier_id: str
    eilig: bool

def verarbeite_transaktion(event):
    match event:
        case NormalerVerkauf(betrag=b):
            print(f"Standardkauf über {b:.2f} € verbucht.")
            
        case ExpressLieferung(betrag=b, kurier_id=k, eilig=True):
            print(f"🚨 Prio-Express über {b:.2f} € an Kurier {k}!")
            
        case ExpressLieferung(betrag=b, kurier_id=k, eilig=False):
            print(f"📦 Standard-Kurier {k} beauftragt.")
            
        case _:
            print("❌ Unbekanntes Event!")
