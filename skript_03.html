1. Warum Modularisierung? Das Problem des Wachstums

Tag 1: Das Ein-Datei-Paradies

  • Ein neues Projekt startet: app.py.
  • 50 Zeilen Code: Man versteht alles auf einen Blick.
  • Keine Imports zwischen eigenen Dateien nötig.
  • Schneller erster Prototyp („Funktioniert doch!“).

  • Enthält: SQL-Queries, HTML-Rendering, Passwort-Hashing, Rabattberechnung, PDF-Export, E-Mail-Versand.

Kognitive Last: Warum unser Gehirn Module braucht

Die 7 ± 2 Regel (Miller's Law)

  • Das menschliche Arbeitsgedächtnis kann gleichzeitig nur etwa 4 bis 7 Informationseinheiten („Chunks“) aktiv halten.
  • Wenn eine Datei 2000 Zeilen hat und 30 Dinge gleichzeitig tut, übersteigt das die menschliche Auffassungsgabe.
  • Folge: Entwickler übersehen Seiteneffekte. Ein Bugfix an Zeile 120 zerstört heimlich eine Funktion in Zeile 1.800.

Was Modularisierung bewirkt

  • Abstraktion: Wir verstehen ein Modul über seine Schnittstelle, ohne den inneren Code zu kennen.
  • Isolation: Änderungen in Modul A können Modul B nicht beschädigen.
  • Paralleles Arbeiten: Teams arbeiten ohne ständige Merge-Konflikte.

2. Anfängerfalle 1: Die „God-Datei“

Der Code-Smell: Alles in app.py

In dieser einzigen Funktion sind vier völlig unterschiedliche Aufgaben vermischt:

  1. HTTP-Routing & Validierung: Liest JSON und prüft Pflichtfelder.
  2. Direkte Datenbank-Abfragen: Führt rohes SQL mit sqlite3 aus.
  3. Geschäftsregeln: Rabattlogik (preis *= 0.9) ist hart einprogrammiert.
  4. Externer Netzwerkaufruf: Verschickt E-Mails via SMTP.

Das fatale Test-Problem:

Wie schreibt man für die Rabattberechnung einen schnellen Unit-Test?
Gar nicht! Man braucht zwingend eine SQLite-Datei und einen erreichbaren SMTP-Server.

# app.py - ALLES in einer Datei (Anti-Pattern)
@app.route('/order', methods=['POST'])
def place_order():
    data = request.json
    if not data.get('items'):
        return jsonify({'error': 'Fehlt'}), 400
    
    # 1. Datenbank & Rabattlogik vermischt
    conn = sqlite3.connect('shop.db')
    cursor = conn.cursor()
    total = 0.0
    for item in data['items']:
        cursor.execute("SELECT preis FROM blumen "
                       "WHERE id = ?", (item['id'],))
        preis = cursor.fetchone()[0]
        if item['menge'] >= 10:
            preis *= 0.9  # 10% Rabatt hartcodiert!
        total += preis * item['menge']
    
    # 2. Persistenz
    cursor.execute("INSERT INTO orders VALUES (?)", 
                   (total,))
    conn.commit()
    conn.close()
    
    # 3. Mailversand
    smtplib.SMTP('smtp.mail.de').sendmail(...)
    return jsonify({'total': total})

2. Anfängerfalle 2: Zirkuläre Importe in Python

# bestellung.py
from kunde import Kunde  # <--- Importiert Kunde

class Bestellung:
    def __init__(self, kunde: Kunde, betrag: float):
        self.kunde = kunde
        self.betrag = betrag

# kunde.py
from bestellung import Bestellung  # <--- Zirkulär!

class Kunde:
    def __init__(self, name: str):
        self.name = name
        self.bestellungen: list[Bestellung] = []

    def neue_bestellung(self, betrag: float):
        b = Bestellung(self, betrag)
        self.bestellungen.append(b)

Der gefürchtete Python-Fehler:

ImportError: cannot import name 'Bestellung' 
from partially initialized module 'bestellung' 
(most likely due to a circular import)

Warum passiert das?

  1. Python lädt bestellung.py.
  2. Zeile 1: from kunde import Kunde.
  3. Python pausiert bestellung.py und beginnt kunde.py auszuführen.
  4. Zeile 1 in kunde.py: from bestellung import Bestellung.
  5. Python prüft sys.modules: bestellung wird gerade initialisiert, hat die Klasse Bestellung aber noch gar nicht erreicht!
  6. Crash: ImportError!

Wie löst man zirkuläre Importe sauber?

Lösung A: Entkopplung über IDs (Empfohlen)

Trennen Sie Daten und Verhalten. Bestellung muss nicht die gesamte Kunde-Instanz kennen – eine kunde_id genügt!

# Saubere Entkopplung über IDs
class Bestellung:
    def __init__(self, kunde_id: str, betrag: float):
        self.kunde_id = kunde_id  # Keine Abhängigkeit!
        self.betrag = betrag

class Kunde:
    def __init__(self, kunde_id: str, name: str):
        self.id = kunde_id
        self.name = name

Design-Regel: Wenn zwei Module sich gegenseitig importieren müssen, gehören sie entweder in dasselbe Modul oder ihr Zusammenspiel muss über IDs / Interfaces entkoppelt werden.

Lösung B: typing.TYPE_CHECKING

Wenn der Import nur für Type Hints benötigt wird, verhindert TYPE_CHECKING den Import zur Python-Laufzeit:

from __future__ import annotations
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    # Wird nur von mypy / IDE gelesen, 
    # NIE zur Python-Laufzeit ausgeführt!
    from bestellung import Bestellung

class Kunde:
    def __init__(self, name: str):
        self.name = name
        self.bestellungen: list[Bestellung] = []

3. Die fundamentalen Prinzipien: Kohäsion (Cohesion)

Was ist Kohäsion?

  • Definition: Kohäsion beschreibt den inneren Zusammenhalt eines Moduls oder einer Klasse.
  • Frage: „Tun alle Teile dieses Moduls Dienst an derselben, klar umrissenen Aufgabe?“

Niedrige Kohäsion (Low Cohesion - Schlecht)

  • Typische Mülleimer-Dateien: utils.py, helpers.py, common.py.
  • Enthält: Datumsformatierung, String-Trimming, DB-Verbindung, Passwort-Hashing.
  • Problem: Niemand weiß, was die Datei eigentlich tut. Jede Änderung birgt Risiken.

Hohe Kohäsion (High Cohesion - Erstrebenswert)

  • Jedes Modul hat eine einzige, klare Verantwortung (Single Responsibility Principle).
graph TD subgraph Low["Niedrige Kohäsion (Mülleimer-Modul)"] U["utils.py"] --> U1["format_date()"] U --> U2["hash_password()"] U --> U3["connect_db()"] end subgraph High["Hohe Kohäsion (Fokussiert)"] R["rabatt.py"] --> R1["MengenRabatt"] R --> R2["TreueRabatt"] R --> R3["GutscheinRabatt"] end style Low fill:#ffebee,stroke:#c62828 style High fill:#e8f8f5,stroke:#27ae60

Beispiel: rabatt.py enthält ausschließlich Rabattregeln. Ändern sich Rabatte, fasst man genau dieses Modul an.

3. Die fundamentalen Prinzipien: Kopplung (Coupling)

Was ist Kopplung?

  • Definition: Kopplung beschreibt den Grad der Abhängigkeit zwischen verschiedenen Modulen.
  • Frage: „Wie viel muss Modul A über das Innenleben von Modul B wissen?“

Enge Kopplung (Tight Coupling - Schlecht)

  • Modul A greift direkt auf interne SQL-Queries oder Variablen von Modul B zu.
  • Ändert sich Modul B minimal, bricht Modul A sofort zusammen.

Lose Kopplung (Loose Coupling - Erstrebenswert)

  • Module kommunizieren ausschließlich über Schnittstellen (Protocol).
  • Modul A weiß was Modul B tut, aber nicht wie.
  • SQLite kann durch PostgreSQL oder In-Memory ersetzt werden, ohne Modul A zu ändern!

Das Zusammenspiel: Die goldene Architekturregel

Die 4 Architektur-Zustände

🏆 Das Ziel: High Cohesion & Low Coupling

  • Hohe Kohäsion: Jedes Modul ist in sich hochgradig fokussiert.
  • Lose Kopplung: Module interagieren nur über schlanke, stabile Schnittstellen (Protocol).
  • Ergebnis: Wartbar, modular, isoliert testbar und zukunftssicher.

⚠️ Die typischen Fehlzustände:

  • Spaghetti-Code: Niedrige Kohäsion + Hohe Kopplung (Alles hängt von allem ab).
  • Verkrampft: Hohe Kohäsion + Hohe Kopplung (Klare Aufgaben, aber wie Kletten verhakt).

4. Python-Bausteine: Module vs. Packages

1. Das Modul (.py-Datei)

  • Jede Python-Datei ist ein eigenständiges Modul mit eigenem Namensraum.
  • Variablen in katalog.py verschmutzen nicht den Namensraum von bestellung.py.
  • Zugriff erfolgt explizit über import:
    import katalog
blume = katalog.Blumenstrauss(...)
  • Best Practice: 1 Modul = 1 fachlich zusammengehöriges Thema (z. B. rabatt.py).

2. Das Package (Verzeichnis)

  • Fasst mehrere verwandte Module zu einer hierarchischen Einheit zusammen.
  • Enthält eine __init__.py zur Paket-Initialisierung.
  • Ermöglicht saubere Unterstrukturen:
    blumenladen/
├── __init__.py
├── katalog/
│   ├── __init__.py
│   ├── modelle.py
│   └── repository.py

Die Rolle der __init__.py: Kapselung & Facade

Wozu dient __init__.py?

  1. Markiert Verzeichnis als Package: Signalisiert Python, dass der Ordner importierbar ist.
  2. Kapselung (Information Hiding): Versteckt interne Dateistrukturen vor der Außenwelt.
  3. Facade-Muster: Exponiert nur die öffentliche API des Pakets über __all__.

Der Vorteil für den Aufrufer:

Nutzer des Pakets müssen nicht wissen, ob Blumenstrauss intern in modelle.py, entities.py oder schema.py liegt. Sie importieren einfach aus dem Package!

# blumenladen/katalog/__init__.py
# Interne Aufteilung bleibt gekapselt.
# Wir exponieren nur die öffentliche Schnittstelle:
from .modelle import Blumenstrauss, Kategorie
from .repository import KatalogRepository

__all__ = [
    'Blumenstrauss', 
    'Kategorie', 
    'KatalogRepository'
]

# Verwendung von außen (sauber & entkoppelt):
from blumenladen.katalog import Blumenstrauss

strauss = Blumenstrauss(name="Rose", preis=25.0)

Information Hiding in Python: Was ist öffentlich, was privat?

Konvention statt Schlüsselwörter

Python hat kein private wie Java. Kapselung beruht auf Namenskonventionen:

  1. Öffentlich (public):
    • Kein Unterstrich: def buche_betrag():
    • Teil der stabilen Schnittstelle. Darf von außen genutzt werden.
  2. Modulintern (_private):
    • Führender Unterstrich: def _pruefe_limit():, _api_key
    • Signal an Entwickler: „Internes Detail! Nicht von außen importieren, kann sich jederzeit ändern.“

Regel: Respektieren Sie den führenden Unterstrich _!

# blumenladen/zahlung/service.py

class ZahlungsService:
    def __init__(self, api_key: str):
        self._api_key = api_key  # Internes Detail
    
    # Öffentliche Methode (Teil der API)
    def buche_betrag(self, betrag: float) -> bool:
        if not self._pruefe_limit(betrag):
            return False
        return self._sende_an_bank(betrag)
    
    # Interne Hilfsmethoden (Finger weg von außen!)
    def _pruefe_limit(self, betrag: float) -> bool:
        return betrag <= 5000.0
        
    def _sende_an_bank(self, betrag: float) -> bool:
        # ... Netzwerkaufruf an Bank ...
        return True

Die Schwachstelle der klassischen Schichtenarchitektur

Das Problem der Datenbank-Dominanz

In der klassischen Schichtenarchitektur hängt die Geschäftslogik direkt von der Datenbank ab:

Geschäftslogik (Business) → Datenbank (Persistence)

  • Die fatale Konsequenz:
    • Entwickler modellieren zuerst Datenbanktabellen (CREATE TABLE ...).
    • Domänenklassen werden zu reinen Abbildern von ORM-Modellen (z. B. SQLAlchemy Base).
    • Die Geschäftslogik ist untrennbar mit SQL und Fremdschlüsseln verstrickt.
  • Test-Albtraum:
    • Jeder Test der Geschäftslogik benötigt eine laufende Datenbank!

Hexagonale Architektur (Ports & Adapters)

Das Prinzip der Dependency Inversion

  • Die Domäne steht im Zentrum: Sie weiß NICHTS von Datenbanken, Webframeworks oder HTTP!
  • Ports (Schnittstellen): Die Domäne definiert Verträge für das, was sie braucht (OrderRepository, PaymentGateway).
  • Adapters (Technik): Externe Komponenten implementieren diese Ports (PostgresRepo, StripeAdapter).

Die Dependency Rule:

Alle Abhängigkeiten zeigen nach INNEN!
Technik hängt von der Domäne ab – niemals umgekehrt!

Ports vs. Adapters im Detail

1. Ports (Schnittstellen / Verträge)

  • Gehören zum inneren Kern.
  • In Python meist als typing.Protocol definiert.
  • Beschreiben WAS getan werden muss, nicht WIE.
  • Unterscheidung nach Cockburn (2 Richtungen):
    • Driving Ports (Primär / Eingehend): Steuern den Kern (z. B. Use-Case-Interfaces, die von Web-API oder CLI aufgerufen werden).
    • Driven Ports (Sekundär / Ausgehend): Werden vom Kern aufgerufen (z. B. Datenbank-Repositories, Payment-Gateways).
  • Beispiele:
    • OrderRepository: Driven Port – „Kann eine Order speichern und laden.“
    • PaymentGateway: Driven Port – „Kann einen Betrag abbuchen.“

2. Adapters (Die konkrete Technik)

  • Liegen am äußeren Rand.
  • Enthalten den konkreten technischen Code.
  • Beispiele für OrderRepository:
    • SqliteOrderRepository (Entwicklung)
    • PostgresOrderRepository (Produktion)
    • InMemoryOrderRepository (RAM-Tests!)
  • Beispiele für PaymentGateway:
    • StripeAdapter (Echtbetrieb)
    • FakePaymentAdapter (Tests ohne Geld)

Analogie: Der Port ist die Wandsteckdose (230V, 50Hz). Der Adapter ist das Netzteil. Welches Netzteil eingesteckt wird, ist der Steckdose egal!

Die Domänenmodelle

  • Value Object OrderItem:
    • Unveränderliche Werte: Artikel-ID, Menge, Einzelpreis.
    • Berechnet den Positionspreis selbstständig.
  • Entity Order:
    • Besitzt eine Identität (id).
    • Fachliche Invarianten: berechne_gesamtsumme().
    • Statuswechsel: markiere_als_bezahlt().
@dataclass
class OrderItem:
    artikel_id: str
    menge: int
    einzelpreis: Money

    def gesamtpreis(self) -> Money:
        return self.einzelpreis.multiply(self.menge)

# bestellung/domain/models.py
from dataclasses import dataclass, field
from core.money import Money

@dataclass
class Order:
    id: str
    kunde_id: str
    items: list[OrderItem] = field(default_factory=list)
    bezahlt: bool = False

    def berechne_gesamtsumme(self) -> Money:
        if not self.items:
            return Money(0.0)
        summe = self.items[0].gesamtpreis()
        for item in self.items[1:]:
            summe = summe.add(item.gesamtpreis())
        return summe

    def markiere_als_bezahlt(self) -> None:
        if self.bezahlt:
            raise ValueError("Bereits bezahlt!")
        self.bezahlt = True

Praxisfall Ada: 3. Der Application Service (services/)

Was macht der Service?

  • Bildet den Use Case ab („Bestellung aufgeben“).
  • Kennt nur die Ports, keine konkrete Datenbank oder APIs!
  • Ablauf im Service:
    1. Gesamtsumme fachlich ermitteln.
    2. Zahlung über den Port anfordern.
    3. Bei Erfolg: Domänenstatus auf bezahlt setzen.
    4. Über das Repository persistieren.

Dependency Injection:

Repositories und Payment-Gateways werden dem Service im Konstruktor übergeben.

# bestellung/services/place_order.py
class PlaceOrderService:
    def __init__(self, repo: OrderRepository, 
                 payment: PaymentGateway):
        self._repo = repo
        self._payment = payment

    def execute(self, order: Order) -> bool:
        summe = order.berechne_gesamtsumme()
        
        # 1. Bezahlung via Port
        if not self._payment.charge(order.kunde_id, summe):
            return False
            
        # 2. Fachlichen Status setzen
        order.markiere_als_bezahlt()
        
        # 3. Speichern via Port
        self._repo.save(order)
        return True

# bestellung/adapters/sqlite_repo.py
import sqlite3
from bestellung.domain.models import Order

class SqliteOrderRepository:
    def __init__(self, db_path: str):
        self.db_path = db_path

    def save(self, order: Order) -> None:
        with sqlite3.connect(self.db_path) as conn:
            conn.execute(
                "INSERT OR REPLACE INTO orders "
                "VALUES (?, ?, ?)",
                (order.id, order.kunde_id, 
                 order.bezahlt)
            )

Adapter 2: Tests (In-Memory!)

# bestellung/adapters/in_memory_repo.py
from typing import Optional
from bestellung.domain.models import Order

class InMemoryOrderRepository:
    """Speichert Daten blitzschnell im RAM."""
    def __init__(self):
        self._storage: dict[str, Order] = {}

    def save(self, order: Order) -> None:
        self._storage[order.id] = order

    def get_by_id(self, order_id: str) -> Optional[Order]:
        return self._storage.get(order_id)

Beide Adapter erfüllen das OrderRepository-Protocol – einer schreibt auf die Festplatte, der andere arbeitet im Arbeitsspeicher!

8. Composition Root: Alles zusammenfügen (main.py)

Was ist die Composition Root?

  • Der einzige Ort in der gesamten Anwendung, an dem konkrete Adapter instanziiert und dem Service übergeben werden.
  • Separation of Concerns: Trennung von Objekterzeugung (hier in main.py) und Objektverwendung (im Service).

Vorher vs. Nachher:

  • ❌ Vorher: Service ruft sqlite3.connect() selbst auf $\to$ Feste Kopplung!
  • ✅ Nachher (DI): Service erhält repo von außen $\to$ Adapter austauschbar!
# main.py - Der Einstiegspunkt
import os
from bestellung.services.place_order import (
    PlaceOrderService
)
from bestellung.adapters.sqlite_repo import (
    SqliteOrderRepository
)
from bestellung.adapters.stripe_adapter import (
    StripePaymentAdapter
)

def bootstrap() -> PlaceOrderService:
    # 1. Konkrete Adapter erzeugen
    repo = SqliteOrderRepository(db_path="shop.db")
    payment = StripePaymentAdapter(
        api_key=os.getenv("STRIPE_KEY", "sk_test")
    )
    
    # 2. Dependency Injection
    return PlaceOrderService(repo=repo, payment=payment)

if __name__ == "__main__":

Zusammenfassung & Best-Practice-Checkliste

Die 5 goldenen Regeln für Modulentwurf:

  1. Eine Datei = Ein logisches Modul: Vermeiden Sie God-Dateien. Mehr als 300 Zeilen sind ein Warnsignal.
  2. High Cohesion, Low Coupling: Was fachlich zusammengehört, bleibt zusammen. Interaktion nur über schlanke Protokolle.
  3. Zirkuläre Importe sofort stoppen: Entkoppeln Sie über IDs oder nutzen Sie typing.TYPE_CHECKING.
  4. Dependency Rule respektieren: Die Domänenlogik darf niemals von Frameworks oder Datenbanken abhängen!
  5. Dependency Injection nutzen: Übergeben Sie Abhängigkeiten über den Konstruktor.
