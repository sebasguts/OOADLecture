Warum Modularisierung? Das Problem des Wachstums

Was ist überhaupt ein „Modul“?

Ein Modul ist ein in sich abgeschlossener Software-Baustein, der eine klar abgegrenzte fachliche Aufgabe erfüllt und mit anderen Bausteinen nur über eine definierte Schnittstelle kommuniziert.

Tag 1: Start in einer einzelnen Datei (app.py)

  • Ein neues Projekt startet mit 50 Zeilen Code in einer Datei.
  • Man überblickt alles sofort, braucht keine import-Befehle für eigene Dateien und hat schnell einen ersten Prototyp.

Tag 60: Unübersichtlicher Monolith

  • app.py ist auf 2.500 Zeilen angewachsen.
  • Enthält gleichzeitig: Webseiten-Buttons, Datenbank-SQL, Passwort-Prüfung, Rabattberechnung, Lagermeldungen und E-Mail-Versand.
  • Folge: Jede Änderung birgt das Risiko unbeabsichtigter Seiteneffekte.

Kognitive Last: Warum unser Gehirn Module braucht

Die 7 ± 2 Regel (Miller's Law)

  • Die Kognitionspsychologie zeigt: Unser menschliches Arbeitsgedächtnis kann gleichzeitig nur etwa 4 bis 7 Informationseinheiten („Chunks“) aktiv verarbeiten.
  • Wenn eine Datei 2.000 Zeilen umfasst und viele verschiedene Aufgaben vermischt, steigt die kognitive Last stark an.
  • Die Folge: Man übersieht Abhängigkeiten. Eine Änderung an der Rabattberechnung in Zeile 120 beeinträchtigt unbemerkt die Lagerverwaltung in Zeile 1.800.

Wie Module das Arbeitsgedächtnis entlasten:

  1. Fokus (Isolation): Wer am Lagermodul arbeitet, betrachtet nur den Code des Lagers – Details des Webshops können ausgeblendet werden.
  2. Schnittstellen statt Innereien: Man muss nur wissen, wie die Schnittstelle aufgerufen wird, nicht wie das Modul intern implementiert ist.
  3. Parallele Teamarbeit: Entwicklerin A arbeitet an lager.py, Entwickler B an verkauf.py – ohne ständige Merge-Konflikte in derselben Datei.

Leitsatz: Wir teilen Software nicht für den Computer in Module auf, sondern um die Komplexität für Entwicklerinnen und Entwickler beherrschbar zu halten.

Anfängerfalle 1: Die „God-Datei“ im Code

Der Code-Smell: Alles in einer Funktion

Schauen wir uns rechts eine typische Anfänger-Funktion in app.py an. Sie vermischt vier völlig verschiedene Welten:

  1. Web-Oberfläche (HTTP/JSON): Liest Browser-Daten aus.
  2. Datenbank-Technik (SQL): Öffnet direkt sqlite3 und schreibt SQL-Befehle.
  3. Fachlogik (Geschäftsregel): Berechnet den 10-%-Mengenrabatt (preis *= 0.9).
  4. Netzwerk-Technik (SMTP): Verbindet sich mit einem E-Mail-Server.

Warum ist das ein Test-Albtraum?

Stellen Sie sich vor, Sie wollen testen, ob der 10-%-Rabatt ab 10 Pflanzen richtig rechnet.
Mit diesem Code geht das nur, wenn gleichzeitig ein Webserver, eine echte SQLite-Datenbankdatei und ein E-Mail-Server laufen!

# ❌ app.py - Anti-Pattern: Die "God-Funktion"
@app.route('/order', methods=['POST'])
def place_order():
    # 1. Web-Schicht (HTTP JSON lesen)
    data = request.json
    if not data.get('items'):
        return jsonify({'error': 'Warenkorb leer'}), 400
    
    # 2. Datenbank & 3. Fachlogik bunt gemischt!
    conn = sqlite3.connect('shop.db')
    cursor = conn.cursor()
    total = 0.0
    for item in data['items']:
        cursor.execute("SELECT preis FROM pflanzen "
                       "WHERE id = ?", (item['id'],))
        preis = cursor.fetchone()[0]
        if item['menge'] >= 10:
            preis *= 0.9  # <-- Fachregel mitten im SQL!
        total += preis * item['menge']
    
    cursor.execute("INSERT INTO orders VALUES (?)", (total,))
    conn.commit()
    conn.close()
    
    # 4. E-Mail-Server direkt aufrufen
    smtplib.SMTP('smtp.mail.de').sendmail(...)
    return jsonify({'total': total})

Grundprinzip 1: Hohe Kohäsion (Innere Zusammengehörigkeit)

Was bedeutet Kohäsion (Cohesion)?

  • Die Frage: „Gehören die Aufgaben, die in diesem Modul stecken, fachlich eng zusammen?“
  • ❌ Niedrige Kohäsion (Sammeldatei):
    Eine Datei hilfsfunktionen.py enthält Datumsformatierung, Passwort-Checks und Blumen-Rabatte.
    Folge: Bei verschiedensten Änderungen muss immer wieder dieselbe Datei bearbeitet werden.
  • ✅ Hohe Kohäsion (Fokussiertes Modul):
    Das Modul lager.py kümmert sich ausschließlich um den Lagerbestand.

Merksatz: Ein Modul hat hohe Kohäsion, wenn man seine Aufgabe in einem einzigen kurzen Satz ohne das Wort „und“ beschreiben kann.

Grundprinzip 2: Lose Kopplung (Äußere Unabhängigkeit)

Was bedeutet Kopplung (Coupling)?

  • Die Frage: „Wie stark hängen zwei Module voneinander ab? Wenn Modul A intern geändert wird, muss dann auch Modul B angepasst werden?“
  • ❌ Enge Kopplung:
    Das Verkaufsmodul greift direkt auf die internen Datenstrukturen oder SQL-Tabellen des Lagermoduls zu.
  • ✅ Lose Kopplung:
    Das Verkaufsmodul ruft nur die definierte Methode lager.gib_bestand(artikel) auf. Wie das Lager intern speichert, bleibt für den Verkauf unsichtbar.

(Schmale Schnittstelle)"| M2 end style Goal fill:#e8f8f5,stroke:#27ae60,stroke-width:2px

Architektur-Regel:
Strebe nach hoher Kohäsion (innerhalb eines Moduls gehört alles fachlich zusammen) und loser Kopplung (zwischen Modulen gibt es möglichst wenige Berührungspunkte).

Wie schneidet man Module fachlich? Bounded Contexts & common

Warum ist es in größeren Systemen problematisch, eine einzige große Pflanze-Klasse für alle Abteilungen zu nutzen?

  • Im Webshop (verkauf): Foto, Beschreibungstext, Verkaufspreis.
  • Im Gewächshaus (lager): Regalnummer, Mindestbestand, Feuchtesensor.
  • Beim Kurier (logistik): Gewicht in kg, Karton-Maße, Lieferadresse.

Die Lösung: Bounded Contexts & das common-Modul

  1. Fachmodule (Bounded Contexts aus DDD):
    Jede Abteilung (verkauf, lager, logistik) bildet ein eigenes Modul mit den für sie relevanten Klassen.
  2. Das common-Modul:
    Grundbausteine, die in mehreren Modulen identisch genutzt werden (Artikel, Geldbetrag, BenutzerRolle), liegen zentral in common.

Design-Entscheidungen dokumentieren & „Fail early, fail fast“

Beim Entwurf tauchen immer Grenzfragen auf, die nicht im Lastenheft standen. Ein sauberer Entwurf dokumentiert jede Entscheidung explizit:

  1. Hat ein neuer Artikel im Inventar sofort Bestand = 0?
    👉 Ja, wird direkt mit 0 angelegt.
  2. Darf ein Artikel gelöscht werden, solange noch Töpfe im Regal (Bestand > 0) stehen?
    👉 Nein! Erst muss der Restbestand ausgebucht werden.
  3. Was passiert, wenn jemand lagere_artikel_ein() für einen unbekannten Artikel aufruft?
    👉 Sofortiger Abbruch mit Fehlermeldung (Fail Fast)!

Das Mantra: „Fail early, fail fast!“

Kehre fehlerhafte Aufrufe niemals unter den Teppich – brich sofort in der ersten Zeile mit einer klaren Exception ab:

class LagerModul:
    def lagere_artikel_ein(self, artikel: Artikel, anz: int) -> None:
        # 1. Fail Fast: Ist der Artikel im Sortiment?
        if artikel.artikel_nr not in self._inventar:
            raise ValueError(
                f"Unbekannter Artikel {artikel.artikel_nr}!"
            )
        # 2. Fail Fast: Keine negativen Mengen!
        if anz <= 0:
            raise ValueError(f"Menge muss > 0 sein (war: {anz})")
            
        self._bestand[artikel.artikel_nr] += anz

Python-Handwerkszeug: Module (.py) vs. Packages (Ordner)

1. Das Python-Modul (Eine .py-Datei)

  • Jede Datei (lager.py) ist ein Modul mit eigenem Namensraum:
    from common import Artikel, Geldbetrag

2. Das Python-Package (Ordner mit __init__.py)

  • Wächst ein Modul, teilen wir es in einen Ordner auf (modelle.py, service.py).
  • Die Datei __init__.py macht den Ordner zum Package und wirkt wie eine Fassade: Sie legt mit __all__ fest, welche Klassen nach außen exportiert werden.

├── lager/
│   ├── __init__.py   <-- Fassade des Lagers

│   └── service.py
└── main.py

from .service import LagerService
__all__ = ["LagerService"]

# In main.py (kurzer, sauberer Import):
from adas_shop.lager import LagerService

Information Hiding in Python: Öffentlich vs. Privat (_)

Ein Modul zeigt nach außen seine Schnittstelle, verbirgt aber seine interne Datenstruktur (Information Hiding / Geheimnisprinzip).

Wie markiert man „Intern / Privat“ in Python?

Anders als Java kennt Python kein erzwingendes Schlüsselwort private. Stattdessen gilt eine Namenskonvention (PEP 8):

  1. Öffentliche Schnittstelle (Kein Unterstrich):
    • lagere_artikel_ein(), gib_bestand()
    • Gehört offiziell zur Modulschnittstelle. Andere Module dürfen diese Methoden aufrufen.
  2. Modulintern / Privat (Führender Unterstrich _):
    • self._bestand, def _hat_genug_vorrat():
    • Kennzeichnet ein internes Implementierungsdetail dieses Moduls, auf das von außen nicht direkt zugegriffen werden darf.
# adas_shop/lager/service.py

class LagerService:
    def __init__(self) -> None:
        # Internes Dictionary (Führender Unterstrich '_'):
        # Kein anderes Modul greift direkt auf _bestand zu.
        self._bestand: dict[str, int] = {}

    # ÖFFENTLICHE SCHNITTSTELLE (Kein Unterstrich):
    def nehme_artikel_aus_lager(self, art_nr: str, anz: int) -> None:
        if not self._hat_genug_vorrat(art_nr, anz):
            raise ValueError("Nicht genügend Bestand im Lager!")
        self._bestand[art_nr] -= anz

    # INTERNE HILFSMETHODE (Führender Unterstrich '_'):
    def _hat_genug_vorrat(self, art_nr: str, anz: int) -> bool:
        aktuell = self._bestand.get(art_nr, 0)
        return aktuell >= anz
Vorteil: Wenn intern _bestand später auf eine andere Datenstruktur umgestellt wird, bleibt der Code aller anderen Module unverändert.

Anfängerfalle 2: Zirkuläre Importe in Python verstehen

Beim Aufteilen von Code auf mehrere Dateien tritt häufig folgender Fehler auf:

ImportError: cannot import name 'Bestellung' 
from partially initialized module 'bestellung' 
(most likely due to a circular import)

Warum passiert dieser Fehler?

  1. In bestellung.py steht oben: from kunde import Kunde.
  2. Python pausiert bestellung.py (bevor class Bestellung definiert wurde) und lädt kunde.py.
  3. In kunde.py steht oben: from bestellung import Bestellung.
  4. Python schaut in das pausierte Modul bestellung – dort existiert die Klasse Bestellung zu diesem Zeitpunkt noch nicht. Das Programm bricht mit einem ImportError ab.

Ursache: Zwei Module importieren sich gegenseitig auf oberster Dateiebene (Zyklus A ⇄ B).

Zirkuläre Importe sauber auflösen (common & ID-Entkopplung)

Lösung 1: Gemeinsame Klassen in common ablegen

Wenn verkauf.py und lager.py beide die Klasse Artikel benötigen, wird Artikel in common.py definiert. Beide Module importieren dann nur in eine Richtung (verkauf → common und lager → common).

Lösung 2: Über IDs statt über Klassen-Objekte referenzieren

Die Klasse Bestellung muss nicht die Klasse Kunde importieren – es genügt, die kunde_id: str zu speichern. Dadurch entfällt der Rück-Import komplett.

# bestellung.py (Kein Import von kunde.py nötig)
from dataclasses import dataclass
from common import Geldbetrag

@dataclass
class Bestellung:
    bestell_nr: str
    kunde_id: str        # Referenz nur über die ID (str)
    betrag: Geldbetrag
Hinweis für Typ-Prüfung (mypy): Wird eine Klasse ausschließlich für Type Hints benötigt, kann sie unter if typing.TYPE_CHECKING: importiert werden (wird zur Laufzeit nicht ausgeführt).

Architekturentscheidung: Wo speichern wir unsere Daten?

Speicher-Alternative Vorteile (+) Nachteile (–)
1. In-Memory (dict im RAM) Sehr schnell (< 1 ms), kein Setup nötig, gut geeignet für Unit-Tests. Bei Programmende gehen alle Daten verloren.
2. Lokale Datei (JSON / CSV) Einfach lesbar, Daten bleiben nach Neustart erhalten. Langsam bei großen Datenmengen; Konflikte bei gleichzeitigem Schreibzugriff.
3. SQL-Datenbank (SQLite / Postgres) Transaktionssicher bei gleichzeitigem Zugriff, skaliert für große Datenmengen. Höherer Einrichtungsaufwand; macht Unit-Tests langsamer.
4. Cloud-Storage Automatische Backups, von mehreren Servern erreichbar. Erfordert Netzwerkverbindung; laufende Kosten.

Konsequenz für die Architektur: Für schnelle automatisierte Unit-Tests benötigen wir In-Memory, für den Produktivbetrieb dagegen eine SQL-Datenbank. Die Fachlogik sollte daher so entworfen werden, dass sich die Speichertechnik austauschen lässt, ohne den Fachcode zu ändern.

Klassische Schichtenarchitektur & die „Datenbank-Dominanz“

Die 3 klassischen Schichten:

  1. Präsentation (Oben – UI / API): Nimmt Benutzereingaben entgegen.
  2. Geschäftslogik (Mitte – Fachmodule): BestellService, LagerService.
  3. Datenzugriff (Unten – Datenbank): Speichert Daten per SQL.

Das Problem dieser Struktur:

Die Abhängigkeiten (import) verlaufen von oben nach unten:

  • Die Geschäftslogik importiert direkt die Datenbank.
  • Folge: Die Fachlogik ist eng an die SQL-Datenbank gekoppelt und lässt sich nicht isoliert im Arbeitsspeicher testen.

Die Lösung: Ports & Adapters (Hexagonale Architektur)

Wir kehren die Abhängigkeitsrichtung mithilfe des Dependency Inversion Principle (SOLID) um:

  1. Innen: Fachlogik (Domäne)
    Kennt nur Fachklassen (Bestellung, Artikel, Geldbetrag) und keinen Datenbank-Code.
  2. Der Port = Die Schnittstelle (typing.Protocol)
    Die Fachlogik definiert als Interface, welche Methoden ein Speicher bereitstellen muss (speichere(b) und lade(id)).
  3. Der Adapter = Die technische Umsetzung (Außen)
    • Adapter A (InMemoryAdapter): Speichert im RAM-dict (für Tests).
    • Adapter B (SqliteAdapter): Speichert in SQLite (für den Betrieb).

Schritt-für-Schritt im Code: 2. Zwei austauschbare Adapter

Nun implementieren wir zwei unterschiedliche Adapter, die beide die Methoden speichere() und lade() des BestellSpeicherPort bereitstellen:

Adapter A: InMemoryBestellSpeicher (Für Tests)

class InMemoryBestellSpeicher:
    """Speichert Bestellungen im RAM-Dictionary."""
    def __init__(self) -> None:
        self._daten: dict[str, Bestellung] = {}

    def speichere(self, bestellung: Bestellung) -> None:
        self._daten[bestellung.bestell_nr] = bestellung

    def lade(self, bestell_nr: str) -> Bestellung | None:
        return self._daten.get(bestell_nr)

Adapter B: SqliteBestellSpeicher (Für den Produktivbetrieb)

import sqlite3

class SqliteBestellSpeicher:

Schritt-für-Schritt im Code: 3. Dependency Injection & Unit-Test

Was bedeutet „Dependency Injection“ (DI)?

Dependency Injection bedeutet: Eine Klasse erzeugt ihren Speicher-Adapter nicht selbst im Inneren, sondern bekommt ihn beim Erstellen von außen über den Konstruktor __init__ übergeben.

  • Im Produktivbetrieb (main.py):
    Dem BestellService wird eine Instanz von SqliteBestellSpeicher übergeben.
  • Im Unit-Test (test_bestellung.py):
    Demselben BestellService wird eine Instanz von InMemoryBestellSpeicher übergeben.
  • Vorteil: Der Unit-Test prüft die Fachlogik direkt im Arbeitsspeicher, ohne dass eine Datenbank eingerichtet sein muss.
# Der Service arbeitet nur gegen das Protocol (den Port):
class BestellService:
    def __init__(self, speicher: BestellSpeicherPort) -> None:
        # Dependency Injection: Adapter wird von außen übergeben
        self._speicher = speicher

    def kaufe_auf_rechnung(self, bestellung: Bestellung) -> None:
        bestellung.markiere_als_bezahlt()
        self._speicher.speichere(bestellung)


# =========================================================
# Unit-Test mit dem In-Memory-Adapter (ohne Datenbank):
# =========================================================
def test_kauf_auf_rechnung() -> None:
    # 1. Arrange: In-Memory-Adapter übergeben
    ram_speicher = InMemoryBestellSpeicher()
    service = BestellService(speicher=ram_speicher)
    
    b = Bestellung("B-100", "KUNDE-1", Geldbetrag(cent=2999))

    # 2. Act: Fachlogik ausführen
    service.kaufe_auf_rechnung(b)

    # 3. Assert: Prüfen, ob bezahlt & im Speicher abgelegt
    gespeichert = ram_speicher.lade("B-100")
    assert gespeichert is not None
    assert gespeichert.bezahlt is True

Zusammenfassung Modul 3

  1. Warum Modularisierung? Unser Arbeitsgedächtnis fasst nur 7 ± 2 Dinge (Millers Law). Die „God-Datei“ (app.py) führt zu unwartbarem Spaghetti-Code.
  2. Hohe Kohäsion & Lose Kopplung: Im Inneren eines Moduls gehört alles eng zusammen (Werkzeugkasten); nach außen kommunizieren Module nur über schmale Schnittstellen.
  3. Fachlicher Modulschnitt: Große Systeme schneidet man nach Fachbereichen (Bounded Contexts: verkauf, lager, logistik) plus einem schlanken common-Modul für gemeinsame Grundtypen (Artikel, Geldbetrag).
  4. Detailliertes Modul-Design & Fail Fast: Jedes Modul dokumentiert seine Schnittstellen und Annahmen. Ungültige Aufrufe werden sofort am Eingang abgewiesen („Fail early, fail fast“).
  1. Python-Handwerkszeug & Zirkuläre Importe: Packages bündeln Dateien hinter einer __init__.py (Empfangsbüro). Ein führender Unterstrich (_) schützt interne Details. Zirkuläre Importe löst man durch Auslagern nach common oder Entkopplung über IDs (kunde_id: str).
  2. Von der Schichten- zur Hexagonalen Architektur: In der klassischen Schichtenarchitektur klebt die Fachlogik an der Datenbank. Mit Ports (Protocol-Steckdose), Adaptern (Technik-Stecker) und Dependency Injection bleibt die Fachlogik zu 100 % frei von Datenbank-Code und lässt sich in Millisekunden In-Memory testen!

Denkpause & Reflexionsfragen

Frage 1: Kohäsion & Kopplung

Ein Entwickler legt eine Datei allgemein.py an, in der er eine Funktion zur MwSt-Berechnung, eine Funktion zum Verbinden mit der SQLite-Datenbank und eine Funktion zum Prüfen der Bodenfeuchte von Orchideen speichert.

  • Welches Prinzip ist hier verletzt und warum?

Frage 2: Zirkuläre Importe & Ports

  1. Warum stürzt Python ab, wenn kunde.py oben from bestellung import Bestellung schreibt und bestellung.py oben from kunde import Kunde?
  2. Warum darf unser BestellService im Inneren nicht einfach self.db = SqliteBestellSpeicher("shop.db") aufrufen?

Antworten zur Selbstkontrolle:

  1. Niedrige Kohäsion (Kram-Schublade):
    Die drei Funktionen haben fachlich nichts miteinander zu tun. Ändert sich die Datenbank oder die Pflanzensensorik, muss jedes Mal dieselbe Sammeldatei angefasst werden.
  2. Importe & Dependency Injection:
    • Beim ersten Import pausiert Python das erste Modul, bevor dessen Klasse fertig geladen ist, und versucht im zweiten Modul genau diese noch unfertige Klasse zu importieren (Circular Import).
    • Wenn der Service SqliteBestellSpeicher selbst erzeugt, ist er fest mit SQLite verlötet (enge Kopplung). Erst durch Übergabe von außen (Dependency Injection gegen den Port) können wir im Test den InMemorySpeicher einstecken!
